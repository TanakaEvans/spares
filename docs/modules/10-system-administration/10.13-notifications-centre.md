# 10.13 Notifications Centre

> One place where every system alert is defined, routed, and read — the bell in the top bar, plus email/SMS delivery. Part of [Module 10: System Administration](../10-system-administration.md). 🆕 New sub-module.

## Purpose

The modules already *generate* events that people must act on — stock below reorder, PO overdue, job past its promised time, customer over credit limit, backup failed, back-ordered part arrived. Without a centre, these live only in reports someone must remember to open. The Notifications Centre turns them into routed, acknowledged alerts: in-app (the bell), email, and SMS (customer-facing ones like "your vehicle is ready").

It is configuration-driven ([configuration-centre.md](../../configuration-centre.md)): which events fire, who receives them, on which channel, with what threshold — all settings, no code changes.

## User Roles & Permissions

| Role | Access |
|------|--------|
| All users | Own bell feed; mark read; own channel preferences |
| Branch Manager | Configure routing for own branch's events |
| Super Admin | Full routing matrix, templates, SMS gateway settings, delivery log |

## Workflow

```
Domain event fires (e.g. StockLevelBelowReorderPoint)
      │
Routing matrix lookup: event → recipients (roles/users) × channels × branch
      │
┌─────┼──────────────┐
▼     ▼              ▼
Bell  Email (queued) SMS (queued, customer events only)
      │
Recipient acts → notification links straight to the record (UI-13)
      │
Mark read / auto-read on visiting the linked record
```

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Bell dropdown | (top bar, both layouts) | Last 15, unread bold, "view all" |
| My notifications | `notifications.index` | Full personal feed, filter by type/date |
| Routing matrix | `admin.notifications.routing` | Event × role × channel grid, per-branch overrides |
| Delivery log | `admin.notifications.log` | Sent/failed email & SMS with retry |

**Primary screen (routing matrix):** rows = catalogued events grouped by module; columns = In-app / Email / SMS; each cell = recipient picker (roles + named users) with branch-override badge, mirroring the Configuration Centre pattern.

## Fields & Validation (routing rule)

| Field | Type | Required | Validation |
|-------|------|----------|-----------|
| event_key | select (catalogue) | ✔ | must exist in code-declared catalogue |
| branch_id | select | — | null = global |
| channel | select: bell/email/sms | ✔ | sms only for events flagged customer-capable |
| recipient_type | select: role/user/customer | ✔ | |
| recipient_id | select | ✔ unless customer | exists |
| digest | select: instant/daily | — | email only |

## Business Rules

1. Events are **declared in code** (typed catalogue per module, like settings); routing/recipients are data. An unrouted event still writes to the admin log — nothing vanishes silently.
2. Every notification deep-links to its record; opening the record marks it read.
3. SMS is reserved for customer-facing and critical-admin events (cost control); per-branch monthly SMS cap is a setting, with a warning at 80%.
4. Email/SMS go through the queue with retry ([architecture.md](../../architecture.md)); failures appear in the delivery log with one-click retry — consistent with the offline-graceful rule in [backup-and-resilience.md](../../operations/backup-and-resilience.md).
5. Digest mode batches low-urgency events into one daily email (time is a setting).
6. Users may mute non-mandatory events for themselves; events flagged `mandatory` (backup failed, credit hold) cannot be muted.

## Edge Cases & Error Handling

- SMS gateway down → messages queue and retry with backoff; log shows "pending retry", never lost.
- Recipient role has no users in a branch → falls back to branch manager + flagged in log.
- Notification storm (e.g. 200 parts hit reorder after a big sale day) → auto-collapses into one summary notification linking the reorder report.
- Deleted/deactivated user in a routing rule → rule flagged broken on the matrix screen.

## Key Tables

`notifications` (Laravel native, per-user feed) · `notification_routes` (the matrix) · `notification_deliveries` (email/SMS log) — schemas follow [database.md](../../coding-standards/database.md) conventions.
