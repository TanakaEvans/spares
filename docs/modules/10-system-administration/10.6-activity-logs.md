# 10.6 Activity Logs

> The system-wide audit trail — who did what, when, and from where. Part of [Module 10: System Administration](../10-system-administration.md). **Status: existing implementation.**

## Purpose

Activity Logs record significant actions across SparesPro: logins, record creation/edits/deletions, permission changes, settings changes, document postings, and sensitive reads. In a cash-and-stock business the audit trail is a control, not a nicety: when a stock take shows 40 missing oil filters, or a customer disputes "I never got that credit note", or a discount pattern looks suspicious on one cashier's shift, the log is where the investigation starts.

The existing implementation captures actions with actor, timestamp, and context. Planned extensions deepen coverage as new modules land: before/after values on edits (so a price change shows 450 → 380, not just "part updated"), and guaranteed hooks from the high-risk flows — discount overrides at POS, credit-limit changes, settings flips, supersession removals, and critical-bulletin acknowledgements ([8.7](../08-vehicle-parts-reference/8.7-technical-bulletins.md)).

Logs are read-only by design: an audit trail that admins can edit is not an audit trail.

## Workflow

```
[User action anywhere in the system]
            │
            ▼
[Logging hook fires (model events /
 explicit log calls in controllers)]
            │
            ▼
[Log entry written: user, action, subject
 (model + id), before/after, IP, timestamp]
            │
            ▼
[Admin investigates] ──► [Filter: user / date range /
                          module / action type / record]
            │
            ▼
[Drill into entry → linked record → related entries
 for the same record (its full history)]
            │
            ▼
[Retention job archives/purges entries
 past the retention window]
```

1. **Capture** — hooks write entries automatically; high-risk flows call the logger explicitly with structured context.
2. **Search** — the log screen filters by user, date range, module/subject type, action, and free text.
3. **Trace a record** — from any entry, view the complete change history of that record in order.
4. **Export** — filtered results export to Excel for auditors.
5. **Retain** — a scheduled job enforces the retention policy (archive then purge).

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Activity logs | `admin.logs.index` | Filterable, paginated log viewer |
| Entry detail | `admin.logs.index` (row expand/modal) | Full payload incl. before/after diff |

**Primary screen — Activity logs**: filter bar (user, date range, module, action type, search) above a reverse-chronological table: timestamp, user, action badge (created/updated/deleted/login/permission/settings), subject ("Part BP-4473", "User T. Moyo"), summary, IP. Row expand shows the before/after diff as a two-column comparison. Server-side pagination throughout — this table gets large.

## Fields & Validation

No user-entry form; the "fields" are the filter inputs:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| user | select | No | any user incl. inactive |
| date_from / date_to | datetime | No | to >= from; default last 7 days |
| module / subject type | select | No | registered loggable models |
| action | select | No | created/updated/deleted/login/logout/permission_change/setting_change/etc. |
| search | text | No | matches summary and subject reference |

Log entries themselves validate at write time: actor id (nullable only for system jobs), action, subject type/id, JSON payload.

## Business Rules

1. Log entries are immutable — no update or delete routes exist; retention purging is the only removal path and is itself logged.
2. Every entry carries the acting user; scheduled/queue jobs log as "System" with the job name.
3. Before/after payloads exclude secrets (password hashes, tokens, SMTP credentials) — the entry records *that* they changed, never the values.
4. High-risk actions are always logged regardless of any verbosity configuration: permission changes, settings changes, credit-limit edits, discount overrides, document deletions/reversals, backup restores, log exports.
5. Viewing sensitive log categories is itself logged (who audited the auditors).
6. Retention default: 24 months online, then archive; finance-relevant entries follow the statutory document retention period instead.
7. Failed logins are logged with IP for lockout analysis (ties into [10.8 Password Policy](10.8-password-policy.md)).
8. Log writes must never break the business action: a logging failure raises an internal alert but the invoice still posts.

## Edge Cases & Error Handling

- **Bulk operations** (price update on 2,000 parts): one summary entry with the batch description plus per-record entries only when before/after capture is enabled for the model — avoids drowning the log while keeping traceability.
- **Deleted user in old entries**: entries keep the user id and display the stored name snapshot "(deactivated)".
- **Clock skew between app servers**: timestamps are DB-generated to keep ordering consistent.
- **Huge payload diffs** (rich-text template edits): payload truncated at a threshold with full copies retained in the archive store.
- **Investigation spanning purged history**: the archive is restorable to a reporting environment; the online screen states the online-window boundary rather than implying "no activity".
- **Log table growth degrading queries**: monthly partitioning/indexed by (subject, created_at) and (user, created_at); the viewer always constrains by date range.
