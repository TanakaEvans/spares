# 10.7 Backup Management

> Scheduled database backups, verification, and restore — the last line of defence. Part of [Module 10: System Administration](../10-system-administration.md). **Status: existing implementation.**

## Purpose

Everything the business knows — stock levels, customer balances, five years of invoices — lives in one database. Backup Management schedules automatic backups, tracks their success or failure, retains them on a rotation, and provides a controlled restore path. For a spares business the loss scenarios are mundane and real: a failed disk on the shop server, a bad migration during an upgrade, ransomware, or an operator error that a point-in-time copy can undo.

The existing implementation provides DB backup scheduling and management via the admin screen. The operational goals this documentation holds it to: backups run unattended on schedule, failures are loudly notified (a silently failing backup is worse than none, because it breeds false confidence), copies exist off the host machine, and restore is tested rather than assumed.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Super Admin | Full: configure schedule, run manual backup, download, restore, delete old backups |
| Owner | View status, run manual backup, download |
| All other roles | None |

## Workflow

```
[Backup schedule configured: e.g. daily 22:00]
                │
                ▼
[Scheduler triggers backup job]
                │
                ▼
[DB dump → compress → checksum]
                │
        ┌───────┴────────┐
        ▼                ▼
[Store locally]   [Copy off-site
                   (cloud/remote disk)]
                │
                ▼
[Verify: size + checksum sanity → record run
 success/failure]
                │
        success │ failure
                ▼        ▼
[Apply retention     [Alert email to admin;
 rotation: prune      run marked failed;
 expired copies]      retry per config]

[Disaster] → [Pick backup → confirm restore →
              maintenance mode → restore →
              integrity checks → resume]
```

1. **Schedule** — frequency and time (typically nightly after close); manual "Backup now" for pre-upgrade snapshots.
2. **Execute** — dump, compress, checksum; runs on the queue/scheduler, never in a web request.
3. **Replicate** — at least one copy leaves the host (configured cloud disk or remote target).
4. **Verify & notify** — each run recorded with size, duration, checksum, status; failures email admins immediately.
5. **Rotate** — retention policy (e.g. 14 daily, 8 weekly, 12 monthly) prunes old copies automatically.
6. **Restore** — admin-only, multi-confirmation flow with automatic pre-restore backup of the current state.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Backup dashboard | `admin.backup.index` | Run history, schedule config, manual actions |

**Layout**: status header (last successful backup, age, next scheduled run — the age turns red past the expected interval); run-history table (timestamp, type auto/manual, size, duration, destination(s), status, actions: download/restore/delete); schedule and retention configuration panel; storage-usage indicator per destination.

## Fields & Validation

Schedule/config form:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| frequency | select | Yes | daily / twice-daily / weekly |
| run_time | time | Yes | valid time; recommended outside trading hours |
| destinations | multi-select | Yes | at least one; off-site destination strongly warned if absent |
| retention (daily/weekly/monthly counts) | integers | Yes | each >= 1; total storage estimate shown |
| notify_emails | email list | Yes | >= 1 valid address for failure alerts |
| compress | boolean | Yes | default true |

Restore flow validates: backup file exists, checksum matches, and the admin has typed the confirmation phrase.

## Business Rules

1. A backup run is only "successful" when the dump completed, the checksum verifies, and all configured destinations received the file — partial success is reported as failure with detail.
2. Failure alerts send on every failed run and a "backup overdue" alert fires if no success within 1.5× the expected interval (catches a dead scheduler, not just failed jobs).
3. Restore always creates an automatic safety backup of the current database first.
4. Restore requires Super Admin, a typed confirmation, and puts the app in maintenance mode for the duration; the action (start, source file, finish, outcome) is written to [Activity Logs](10.6-activity-logs.md) — the log entry for the restore survives because it is also written after restore completes.
5. Backup files are encrypted at rest when stored off-site; download of a backup file is logged.
6. Retention pruning never deletes the most recent successful backup regardless of policy.
7. Manual pre-upgrade backups can be pinned ("keep") to exempt them from rotation.
8. Uploaded/attached files (logos, document PDFs) are included in the backup scope or covered by a parallel file-storage backup — the dashboard states which, so nobody assumes coverage that isn't configured.

## Edge Cases & Error Handling

- **Backup runs during heavy writes** (late invoicing): dumps use a consistent-snapshot mode so the copy is transactionally coherent.
- **Destination full / cloud credentials expired**: run fails with the destination error surfaced verbatim in the run detail; other destinations still receive their copy and the run reports partial failure.
- **Very large database vs backup window**: duration trend is visible in run history; the dashboard warns when duration approaches the schedule interval.
- **Restore of an old backup after schema migrations**: the restore flow warns when the backup's schema version differs from the application's and requires acknowledging that migrations will run (or the app version must match).
- **Ransomware on the host**: off-site copies with independent credentials are the mitigation; the config screen warns whenever the only destination is the local disk.
- **Checksum mismatch on a stored file** (bit rot): flagged in the run history retroactively by a periodic verification job; the backup is marked unusable.
