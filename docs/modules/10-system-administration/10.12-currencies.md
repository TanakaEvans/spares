# 10.12 Currencies

> Multi-currency setup and dated exchange rates for a business trading across borders. Part of [Module 10: System Administration](../10-system-administration.md). **Status: new.**

## Purpose

A Southern/Central African spares business rarely lives in one currency: stock is imported from South African suppliers invoicing in ZAR, from overseas in USD, while local sales may run in USD, ZWG, or a mix. The Currencies sub-module defines which ISO 4217 currencies the system knows (code, name, symbol, decimal places), designates exactly one as the base currency, and maintains dated exchange rates between them.

Rates are date-effective by design: the ZAR/USD rate on the day a purchase order was placed differs from the rate on payment day, and both must be preserved. Historical reporting uses the rate that applied at transaction date — never today's rate retroactively — and the gap between PO-date and payment-date rates posts to a dedicated FX variance GL account per the parent doc's business rules.

The base currency is the accounting spine: the GL, stock valuation, and consolidated reports are all expressed in it, which is why it locks permanently once transactions exist.

## Workflow

```
[Company setup: choose base currency
 (is_base = true, e.g. USD)]
            │
            ▼
[Add trading currencies: ZAR, ZWG, ...
 code, name, symbol, decimal places]
            │
            ▼
[Capture exchange rates: from → to, rate,
 effective_date, source (manual/api)]
            │            ▲
            │            │ daily API pull or
            │            │ manual entry
            ▼            │
[Foreign-currency document created
 (ZAR supplier invoice, USD quote)]
            │
            ▼
[System picks the rate effective on the
 document date → stores it ON the document]
            │
            ▼
[Payment at a different date/rate →
 FX gain/loss posted to FX variance GL]
```

1. **Base currency** — set once at [Company Setup](10.2-company-setup.md); everything consolidates into it.
2. **Add currencies** — each with ISO code, symbol, and `decimal_places` (usually 2) controlling display and rounding.
3. **Maintain rates** — manual entry by accounts, or an API feed marked `source = api`; one rate per pair per effective date.
4. **Apply** — documents in a foreign currency snapshot the applicable rate at creation; the stored rate, not a lookup, is used for all later maths on that document.
5. **Settle** — payments revalue at the payment-date rate; the difference posts automatically to the FX variance account.

| Screen | Route | Purpose |
|--------|-------|---------|
| Currencies list | `admin.currencies.index` | Currency records, base badge, active toggles |
| Exchange rates | `admin.exchange-rates.index` | Rate history per pair, add rate |

**Primary screen — Exchange rates**: currency-pair selector (e.g. ZAR → USD) with a dated rate table (effective date, rate, source, entered by) and a sparkline of the last 90 days; "Add rate" captures rate + effective date. A staleness banner appears when the newest rate for an active pair is older than a configurable number of days.

## Fields & Validation

Currency:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| code | text | Yes | exactly 3 chars, ISO 4217, uppercase, unique |
| name | text | Yes | max 50 |
| symbol | text | Yes | max 5 |
| decimal_places | integer | Yes | 0–4 (usually 2) |
| is_base | boolean | Yes | exactly one true system-wide |
| is_active | boolean | Yes | base currency cannot be deactivated |

Exchange rate:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| from_currency_id / to_currency_id | select | Yes | distinct, both active |
| rate | decimal(15,6) | Yes | > 0; warn if it deviates > 20% from the previous rate (fat-finger guard) |
| effective_date | date | Yes | unique per pair; not more than 1 day in the future |
| source | select | Yes | `manual` or `api` |

## Business Rules

1. Exactly one base currency; it is set at company setup and **cannot be changed after any transaction exists** (parent-doc rule 1). Changing base is a re-implementation event, not a setting.
2. Rates are date-specific and historical rates are immutable once any document has consumed them — corrections are new rows for the same date only while unconsumed, otherwise an adjusting entry in Finance.
3. Rate resolution for a document date: the most recent rate with `effective_date` <= document date; no rate found = the document cannot be captured in that currency (fail closed, with a prompt to enter a rate).
4. FX gain/loss between PO-date rate and payment-date rate posts to the dedicated FX variance GL account (parent-doc rule 3); the posting references both rates.
5. Inverse rates are derived (1 ÷ rate), not stored twice, unless an explicit inverse row exists (some desks quote asymmetric rates); explicit wins over derived.
6. `decimal_places` drives rounding at line level; rounding differences on totals post to a rounding account, never silently absorbed.
7. Deactivating a currency blocks new documents in it; open documents (unpaid ZAR invoices) continue to settle normally.
8. Manual rates are activity-logged with the entering user; `api` rates record the feed and pull time.

## Edge Cases & Error Handling

- **Hyperinflation-scale moves / redenomination** (ZWL → ZWG history): handled as a *new* currency code with its own rates; the old code deactivates with history intact — never rate-edited in place.
- **Backdated document needing a backdated rate**: allowed if a rate exists on/before the date; entering a late historical rate is permitted while nothing consumed the gap, and logged.
- **API feed outage**: the last rate keeps resolving (rule 3's "on or before" logic) while the staleness banner and an optional alert nag accounts; nothing blocks until staleness exceeds the hard limit configured.
- **Rate entered with from/to inverted** (0.054 instead of 18.52): the 20% deviation guard plus an on-screen sanity line ("1 USD = 18.52 ZAR — is this right?") catch it before save.
- **Two rates needed same pair, same day** (official vs interbank): the model stores one per pair/date; businesses needing dual rates model them as distinct source-suffixed pairs — documented limitation.
- **Payment in a third currency** (ZAR invoice paid in USD): converted through base at the payment date's rates; both legs post with their rates recorded.
- **Zero-decimal currency** (e.g. JPY for a Japanese parts order): `decimal_places = 0` renders and rounds correctly on documents and templates.
