# 10.1 Users & Roles

> User accounts and route-based RBAC — who can log in and what they can touch. Part of [Module 10: System Administration](../10-system-administration.md). **Status: existing implementation.**

## Purpose

Users & Roles is the security foundation of SparesPro. Every other module's permission checks — from a cashier's discount ceiling to an accountant's view of the P&L — resolve through this sub-module. The existing implementation provides user CRUD (`UserController`), role CRUD with bulk assign/remove (`RoleController`), route-based permissions through the `role_routes` pivot, and enforcement middleware (`EnsureHasRole`, `AdminMiddleware`).

The RBAC model is deliberately route-based: `User → has many → Roles → has many → SystemRoutes`. A role is a named bundle of routes; granting a role grants its routes. This maps naturally onto Laravel's named routes and lets new modules plug in by seeding `SystemModule` and `SystemRoute` records, then assigning them via the Bulk Assign interface — no code change to the permission layer.

For the motor-spares context the parent doc defines twelve suggested default roles, from Super Admin down to Reports Only, matching the real division of labour in a parts business: counter staff sell, buyers purchase, warehouse receives, accounts collects, workshop wrenches — and nobody sees more than their job needs.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Super Admin | Full user/role CRUD, role-route assignment, all modules |
| Branch Manager | View users of own branch; cannot change roles |
| All other roles | Own profile only (password, contact details) |

Suggested business roles managed here (see parent doc for the full module-access matrix): Super Admin, Branch Manager, Sales Manager, Cashier/Counter Staff, Purchasing Officer, Warehouse Staff, Accounts Clerk, Accountant, Workshop Foreman, Technician, Receptionist, Reports Only.

## Workflow

```
[New employee hired]
        │
        ▼
[Admin creates user: name, email, branch, department]
        │
        ▼
[Assign role(s) from the role list]
        │
        ▼
[User logs in → middleware (EnsureHasRole /
 AdminMiddleware) checks each request's route
 against the user's roles' route grants]
        │
        ▼
[Job change → roles reassigned]   [Leaver → deactivate account]

New module rollout:
[Seed SystemModule + SystemRoute records]
        │
        ▼
[Bulk Assign: tick routes per role] → [Roles updated everywhere]
```

1. **Create user** with identity, branch, and department; initial password per [password policy](10.8-password-policy.md).
2. **Assign roles** — one or more; effective permissions are the union of all assigned roles' routes.
3. **Enforce** — middleware checks every named route against the user's grants; unauthorised requests get 403.
4. **Maintain roles** — the Bulk Assign interface adds/removes route grants for a role in one operation, module by module.
5. **Offboard** — deactivate (never delete) so document authorship and activity logs stay intact.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Users list | `auth.users.index` | All users, search, status, roles |
| User create/edit | `auth.users.create` / `.edit` | User form |
| Roles list | `auth.roles.index` | Role list with user counts |
| Role detail / Bulk Assign | `auth.roles.*` | Grant/revoke routes per role, grouped by module |

**Primary screen — Users list**: table of name, email, branch, department, role badges, active status, last login. Filters by branch/role/status. Row actions: edit, reset password, deactivate. The role edit screen groups routes by `SystemModule` with per-module select-all — the Bulk Assign workflow from the existing implementation.

## Business Rules

1. Permissions are additive — a user with Cashier + Reports Only holds the union of both routes; there are no deny rules.
2. At least one active Super Admin must exist; the system blocks deactivating or de-roling the last one.
3. Users are deactivated, never deleted — invoices, GRNs, job cards, and activity logs reference them forever.
4. A role cannot be deleted while users hold it; reassign first.
5. Role/route changes take effect on the user's next request (no re-login required) and are written to the [activity log](10.6-activity-logs.md).
6. Branch assignment scopes data visibility in modules that filter by branch (reports, stock, sales); roles control *function*, branch controls *scope*.
7. New modules must seed `SystemModule` and `SystemRoute` records before their routes can be granted — unseeded routes fail closed (no access).
8. Sensitive permission grants (financial reports, margin visibility, user management) are highlighted in the Bulk Assign UI so an admin sees what a tick exposes.

## Edge Cases & Error Handling

- **User locks themselves out** (forgotten password + policy lockout): admin-initiated reset issues a temporary password that must change at next login.
- **Admin edits their own roles**: removing your own admin route access warns before saving; removing the last Super Admin is blocked outright.
- **Employee covering two jobs** (cashier who also receives stock): assign both roles rather than widening either role — keeps role definitions clean.
- **Route renamed in code but not re-seeded**: enforcement fails closed; the admin screen shows orphaned route grants for cleanup.
- **Deactivated user's scheduled reports and approvals**: deactivation lists dependent artefacts (schedules, open approvals) for reassignment (see [9.8](../09-reports-analytics/9.8-scheduled-reports.md)).
- **Concurrent role edits by two admins**: last save wins on the pivot but both edits appear in the activity log for reconstruction.
