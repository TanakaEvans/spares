# 10.8 Password Policy

> Configurable password rules, expiry, and lockout protecting every account. Part of [Module 10: System Administration](../10-system-administration.md). **Status: existing implementation.**

## Purpose

Password Policy defines and enforces credential rules for all SparesPro users: minimum length and complexity, expiry, reuse prevention, and failed-attempt lockout. In a shop environment the realistic threats are close-range: shared terminals at the counter, a leaver who remembers a colleague's password, a written-down password taped to the till. Policy enforcement plus lockout plus the failed-login trail in [Activity Logs](10.6-activity-logs.md) addresses exactly those.

The policy is configuration, not code: the admin tunes the rules to the business's risk appetite (a stricter regime for admin/finance roles is a planned extension), and enforcement happens uniformly at every point a password is set — self-service change, admin reset, and first-login forced change.

Because POS staff log in dozens of times a day, the policy must balance security with counter speed; the settings deliberately expose expiry and lockout windows rather than hard-coding aggressive defaults that would push staff into workarounds.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Super Admin | Edit policy settings; unlock locked accounts; force resets |
| Owner | View policy; unlock accounts |
| All roles | Subject to the policy; self-service password change |

## Workflow

```
[Admin configures policy: length, complexity,
 expiry days, history depth, lockout threshold]
                    │
                    ▼
[User sets/changes password] ──► [Validated against
                                  policy + history]
                    │
                    ▼
[Login attempts] ──► [Failure counter per account]
                    │
        threshold   │ reached
                    ▼
[Account locked for lockout window]
        │                     │
        ▼                     ▼
[Auto-unlock after      [Admin manual unlock
 window expires]         (logged)]

[Expiry reached] → [Forced change at next login]
[Admin reset]    → [Temporary password, must
                    change at first login]
```

1. **Configure** — the policy screen sets the rule set; changes apply to future password events, never invalidating current passwords retroactively (except via forced-reset).
2. **Enforce at set-time** — every password creation/change path validates length, character classes, and reuse history.
3. **Enforce at login** — expired passwords force a change; failed attempts count toward lockout.
4. **Lock & unlock** — lockout after N failures within the counting window; auto-unlock after the lockout duration or admin unlock.
5. **Audit** — failed logins, lockouts, unlocks, resets, and policy changes are all activity-logged.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Password policy settings | `admin.settings.index` (security section) or dedicated screen | Policy configuration |
| Locked accounts | `auth.users.index` (filter: locked) | View/unlock locked users |
| Change password | user profile | Self-service change with live rule checklist |

**Primary screen — Policy settings**: a form of the rule set with plain-language explanations and a live example meter ("a compliant password looks like…"). Below, current stats: accounts locked now, passwords expiring within 14 days, accounts on temporary passwords.

## Fields & Validation

Policy configuration:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| min_length | integer | Yes | 8–64 |
| require_uppercase / lowercase / number / symbol | boolean | Yes | at least two classes required overall |
| expiry_days | integer | Yes | 0 (never) – 365 |
| history_depth | integer | Yes | 0–24 previous passwords blocked |
| lockout_threshold | integer | Yes | 3–10 failed attempts |
| lockout_window_minutes | integer | Yes | counting window, 5–60 |
| lockout_duration_minutes | integer | Yes | 5–1440 |
| force_change_on_first_login | boolean | Yes | default true |

Password change form: current password (self-service only), new password (validated live against the rule checklist), confirmation must match.

## Business Rules

1. Policy applies at set-time and login-time; tightening the policy does not invalidate existing passwords until their next change or an explicit forced reset.
2. Passwords are stored only as hashes (bcrypt/argon2); history comparison uses stored hashes of prior passwords, never plaintext.
3. Admin resets issue a temporary password flagged must-change; the temporary password also has a short validity (e.g. 24 h).
4. Lockout counts failures per account within the counting window; a successful login resets the counter.
5. The last active Super Admin cannot be locked out permanently — admin unlock plus a documented recovery path (console command) must exist.
6. All lockouts, unlocks, resets, and policy edits are written to [Activity Logs](10.6-activity-logs.md) with actor and target.
7. Password fields, hashes, and temporary passwords never appear in logs, emails, or exports; reset communication carries a link/temporary secret through a controlled channel only.
8. Planned extension: per-role overlays (e.g. Finance and Super Admin roles require longer minimum length and shorter expiry than counter roles).

## Edge Cases & Error Handling

- **Shared counter terminal, wrong user selected repeatedly**: lockout messages avoid confirming whether the *password* or *account* was wrong; the lockout notice shows remaining minutes so staff don't hammer it further.
- **Lockout during a busy Saturday at POS**: admin unlock from the users screen is immediate; the auto-unlock window keeps the outage bounded even with no admin present.
- **Expiry lands on all staff the same day** (policy enabled long after go-live): expiry is staggered from each user's last-change date, not the policy-change date, avoiding a mass same-day reset.
- **User forgets password and email is unavailable** (no personal mailboxes for counter staff): admin reset with verbal handover of the temporary password is the fallback; must-change-at-login limits the exposure.
- **Brute force across many accounts from one source**: per-account lockout plus the failed-login IP trail in activity logs; rate limiting at the login route is the complementary control.
- **Temporary password expires unused**: account returns to "reset required" state; a fresh reset is issued rather than reactivating the old secret.
