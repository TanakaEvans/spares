# 10.11 Email Configuration

> SMTP transport plus the template library for every email the system sends. Part of [Module 10: System Administration](../10-system-administration.md). **Status: new.**

## Purpose

Email Configuration makes SparesPro's outbound mail work and look right. It has two halves. Transport: the SMTP (or API mailer) settings — host, port, encryption, credentials, from-address — that every message rides on. Content: the `email_templates` library, one template per message type (`invoice`, `statement`, `quote`, `po`, `low_stock_alert`, …) with a variable-substituting subject and HTML body, plus default CC addresses.

The transactional matrix from the parent doc defines what fires when: invoice created → customer (invoice PDF attached); quote created → customer; PO confirmed → supplier; statement generated → customer; low stock alert → buyer; job card completed → customer; scheduled report → configured recipients. Each trigger pairs a template with an attachment rendered by [Print Templates](10.10-print-templates.md).

Templates use variables like `{customer_name}` and `{invoice_number}` so the accounts clerk can adjust wording ("Please find attached tax invoice {invoice_number}…") without a developer, while the trigger wiring stays in code.

## Workflow

```
[Configure SMTP: host, port, encryption,
 username, password, from name/address]
            │
            ▼
[Send test email → verify receipt]
            │
            ▼
[Author templates per type: subject + HTML body
 with variables, default CC, active toggle]
            │
            ▼
[Business event fires (invoice posted,
 stock below reorder, job completed)]
            │
            ▼
[Queue mail job: resolve template → substitute
 variables → attach rendered PDF → send]
            │
      ┌─────┴──────┐
      ▼            ▼
[Delivered:    [Failure: retry with backoff →
 logged with    mark failed, surface on the
 recipient +    document ("email failed") +
 timestamp]     admin alert]
```

1. **Transport setup** — SMTP details entered once, verified with a test send before anything relies on it.
2. **Template authoring** — per type: subject with variables, HTML body, CC defaults, active flag. Inactive template = that email type silently disabled (deliberately).
3. **Trigger** — module events queue mail jobs; email sending never blocks the business transaction (an invoice posts even if mail is down).
4. **Substitute & attach** — variables resolve from the triggering document; the PDF is rendered via the print pipeline and attached.
5. **Track** — each send is logged against the source document (sent/failed, recipient, time), so "did the customer get their statement?" is answerable.

## Fields & Validation

SMTP settings:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| host | text | Yes | hostname format |
| port | integer | Yes | 1–65535 (587/465/25 hints) |
| encryption | select | Yes | tls / ssl / none (none warned) |
| username / password | text / secret | Per server | password stored encrypted, never redisplayed |
| from_address | email | Yes | valid; SPF/DKIM alignment note shown |
| from_name | text | Yes | max 100 |

Email template:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| type | select | Yes | one per type (unique) |
| subject | text | Yes | max 255; unknown `{variables}` rejected against the type's variable list |
| body | HTML | Yes | sanitised; unknown variables rejected; must include at least the primary reference variable (e.g. `{invoice_number}`) for document types |
| cc | text | No | comma-separated valid emails |
| is_active | boolean | Yes | — |

## Business Rules

1. Variable validation is type-scoped: `{invoice_number}` is available on the invoice template, not on `low_stock_alert`; saving with an undefined variable fails with the offending token named.
2. Mail is always queued; a transport outage delays delivery but never blocks posting documents.
3. Failed sends retry (3× with backoff), then mark the document's email status failed and notify admins; the document screen offers "resend".
4. Deactivating a template disables that email type without deleting the wording; triggers check `is_active` before queuing.
5. SMTP password is write-only: stored encrypted, masked in the UI, absent from logs and backups' plaintext exports.
6. Customer-facing sends respect the customer's email-opt-out flag (statements/invoices are transactional and exempt where law treats them so; marketing-flavoured types respect opt-out strictly).
7. Every send is logged (type, recipient, document ref, status, timestamp) — visible on the source document and in [Activity Logs](10.6-activity-logs.md).
8. The from-address must be a domain the business controls; the screen warns about SPF/DKIM so invoices don't land in spam.
9. Notification-type sends (low stock, PO overdue, job overdue) are additionally gated by the toggles in [10.5 System Settings](10.5-system-settings.md).

## Edge Cases & Error Handling

- **Customer has no email address**: the trigger skips gracefully and marks the document "not emailed — no address"; POS can still print.
- **SMTP credentials expire** (provider password rotation): the first failure alerts admins with the transport error; queued mail is retried after credentials are fixed rather than lost.
- **Template edited while jobs are queued**: jobs snapshot the rendered content at queue time, so an edit never half-applies to an in-flight batch.
- **Oversized attachment** (500-line invoice PDF): attachment size cap with automatic fallback to a download link in the body.
- **Bounces**: recorded against the document when the transport reports them; repeated bounces flag the customer's email on their record.
- **Test send with unsaved changes**: test uses the editor's current (unsaved) content, clearly labelled TEST in the subject.
- **HTML body with unsafe markup pasted in**: sanitiser strips scripts/forms on save; the preview shows the sanitised result.
