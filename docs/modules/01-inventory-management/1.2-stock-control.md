# 1.2 Stock Control

> Real-time per-branch stock levels, an immutable movement ledger, adjustments, and inter-branch transfers. Part of [Module 1: Inventory Management](../01-inventory-management.md).

## Purpose

Stock control answers the question the counter asks a hundred times a day: "how many do we actually have, here, right now?" It maintains per-branch quantities for every part — on hand, reserved against open sales orders, on order with suppliers, and in transit between branches — so that availability shown at POS is trustworthy. If the screen says 4 brake pad sets for a Toyota Hilux (`BRK-PAD-0122`) are on the shelf and there are only 2, the business loses the sale and the customer.

Every quantity is derived from an append-only stock ledger. Nothing edits a balance directly: a sale, a goods receipt, an adjustment, a transfer dispatch each write a ledger row, and `stock_levels` is a materialized cache of those rows. This gives a complete audit trail — any balance can be reconstructed and any discrepancy traced to the exact transaction, user, and timestamp that caused it.

The sub-module also covers controlled corrections (adjustments with reason codes such as damage, theft, found) and inter-branch transfers with a dispatch/receive handshake, so stock is never double-counted or lost "in the van" between branches.

| System Admin | Rebuild `stock_levels` cache from ledger; view all branches |

## Workflow

Adjustment workflow (transfers follow the status chain in the parent doc):

```
Discrepancy noticed (damage / count wrong / item found)
        │
        ▼
Create adjustment (branch, reason code, lines: system qty vs actual)
        │
        ▼
   value ≤ threshold ──────────────► Post immediately
        │
   value > threshold
        ▼
Manager review ──► Approve ──► Post (ledger entries written)
        │
        └──► Reject → back to draft with comments
```

1. Storeman creates an adjustment, picks a reason code (`damage`, `write_off`, `correction`, `found`, `theft`, `expiry`) and enters actual quantities per part/bin.
2. The system computes variance and its value at current unit cost.
3. If total absolute value exceeds the configured threshold (e.g. $500), status moves to awaiting approval; otherwise the creator may post directly.
4. On post, one `ADJUSTMENT_IN`/`ADJUSTMENT_OUT` ledger row per line is written and `stock_levels` is updated by the service event.
5. Transfers: request → approve → dispatch (source stock down, `qty_in_transit` up) → receive (destination stock up); short receipts create a variance line for investigation.

## Fields & Validation

Main form: stock adjustment.

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| branch_id | FK | Yes | User must belong to or manage this branch |
| reason_code | enum | Yes | One of `damage`, `write_off`, `correction`, `found`, `theft`, `expiry` |
| notes | text | Cond. | Required when reason is `theft` or `write_off` |
| lines[].part_id | FK | Yes | Active part; serial-tracked parts require serial selection |
| lines[].bin_location_id | FK | Yes | Must belong to the same branch |
| lines[].qty_actual | decimal(10,2) | Yes | ≥ 0; decimals only for fractional UoM (litre, metre) |
| lines[].qty_system | decimal(10,2) | Auto | Snapshotted when the line is added |
| lines[].unit_cost | decimal(15,2) | Auto | Pulled from current average cost; editable by manager only |

## Business Rules

1. `stock_ledger` is append-only. Corrections are new reversing entries, never edits or deletes.
2. `qty_on_hand` in `stock_levels` is a cache of the ledger sum per part+branch; a nightly reconciliation job compares cache to ledger and alerts on drift.
3. Adjustments with absolute value above the configured threshold require manager approval before posting; the threshold is per-branch configurable.
4. Transfers decrement source `qty_on_hand` only at dispatch, increment destination only at receive; between the two events the quantity lives in `qty_in_transit` on the source branch.
5. Negative stock is blocked by default. A transaction that would drive `qty_on_hand - qty_reserved` below zero is refused unless the branch has `allow_negative_stock` enabled, in which case it posts with a warning flag.
6. Reserved quantity can never exceed on-hand plus in-transit-inbound; order confirmation checks this.
7. Posting is atomic per document: either every line writes its ledger entry and cache update, or none do (DB transaction).
8. Unit cost on `ADJUSTMENT_IN` for `found` items uses the part's current average cost, not zero — otherwise stock value is understated.
9. A cancelled transfer after dispatch requires a receive-back at the source branch; stock never silently reappears.

## Edge Cases & Error Handling

- **Two cashiers sell the last unit simultaneously**: ledger posting runs inside a transaction with a row lock on `stock_levels`; the second sale fails availability re-check and the cashier sees "stock just sold at another till".
- **Transfer received short** (10 dispatched, 8 arrive): receiver records 8; the 2-unit gap stays in `qty_in_transit` and raises an investigation task; resolution posts either a receive-back or a `theft`/`damage` adjustment at the source.
- **Adjustment on a part mid-stock-take** with `freeze_movements` on: blocked with "branch frozen for stock take STK-2026-0014".
- **Cache drift detected** (ledger says 12, cache says 11): reconciliation job corrects the cache from the ledger and logs the event; the ledger is never altered.
- **Serial-tracked part adjusted out** without selecting serials: validation blocks the line until specific serial numbers are chosen.
- **Backdated GRN arrives after later sales already posted**: ledger rows are ordered by insertion; running balance recomputes forward from the insertion point in the nightly job.
- **Approval threshold changed** while adjustments are pending: pending documents keep the threshold captured at creation.
