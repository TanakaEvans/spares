# 1.6 Parts Fitment Guide

> Vehicle compatibility matrix — which parts fit which vehicles, by make/model/variant/year/engine. Part of [Module 1: Inventory Management](../01-inventory-management.md).

## Purpose

The fitment guide answers the two questions that define counter service in the spares trade: "which parts fit this vehicle?" and "which vehicles does this part fit?". A customer with a 2015 Toyota Hilux 2.5 D-4D (2KD-FTV engine) needs the *right* oil filter — sell them the 2.8 GD-6 filter and it comes back tomorrow with an annoyed customer and a restocking cost. Wrong-part returns are the single largest avoidable cost at the counter, and every one erodes the trust that keeps trade customers loyal.

Fitment data links a part to a make, optionally narrowed to model, variant, year range, and engine code. Broad records ("fits all Hilux") coexist with precise ones ("Hilux 2.8 GD-6, 2015–, engine 1GD-FTV"). At POS, when a customer vehicle is selected or a registration is looked up, the parts search filters or flags results: confirmed fit, possible fit (unverified), or known non-fit.

Data arrives from three sources of differing trustworthiness: imported catalogues (TecDoc), supplier fitment files, and manual entries by staff who have physically verified a fit. Keeping these sources distinguishable — and keeping imported data read-only — is what keeps the matrix trustworthy over years of accumulation.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Cashier | View fitments at POS; report a suspected wrong fitment |
| Counter Sales (senior) | Add `manual` fitment records (unconfirmed) |
| Inventory Clerk | Add/edit `manual` records, run supplier imports |
| Inventory Manager | Confirm fitments, resolve reported errors, delete manual records |
| System Admin | Manage TecDoc imports, bulk operations |

## Workflow

```
Customer at POS gives vehicle (reg lookup or manual pick)
        │
        ▼
Parts search filtered/flagged by fitment:
   ✔ confirmed fit   ? unverified fit   ✖ known non-fit
        │
        ├── fit correct → sale proceeds, nothing to do
        │
        └── staff discover gap or error
                 │
                 ▼
        Add manual fitment / report wrong fitment
                 │
                 ▼
        Manager reviews report → confirm, correct, or reject
                 │
                 ▼
        Confirmed record now shows ✔ for future sales
```

1. Vehicle context is set at POS from the customer's registered vehicles or a make/model/year picker.
2. Search results carry a fitment badge; selecting a "known non-fit" part requires an explicit override with reason (recorded on the sale line).
3. When a fitment is missing (part fits but no record), senior counter staff add a `manual` record on the spot — it shows as unverified until a manager confirms it.
4. A wrong-part return (Module 2.5) with reason "does not fit" auto-raises a fitment review task against the record that recommended it.
5. Supplier and TecDoc imports run per catalogue file; imported rows are stamped with their `source` and never editable in place.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Part fitments tab | `inventory.parts.show` | All vehicles a part fits; add/edit manual records |
| Vehicle parts lookup | `inventory.fitments.vehicle` | Pick a vehicle, browse compatible parts by category |
| Fitment review queue | `inventory.fitments.review` | Reported errors and unconfirmed manual records |

**Primary screen — Part fitments tab (on `Parts/Show.jsx`):** Header repeats the part card (number, description, brand). Main area is a table of fitment rows: make, model, variant, year range, engine code, source badge (`tecdoc` grey, `supplier` blue, `manual` amber until confirmed, green when confirmed), and notes ("front axle only", "not for models with ABS"). Actions per row: confirm (manager), edit/delete (manual rows only). "Add fitment" opens a cascading picker: make → model → variant → years → engine.

## Fields & Validation

Main form: fitment record.

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| part_id | FK | Yes | Active part |
| vehicle_make_id | FK | Yes | From vehicle reference data |
| vehicle_model_id | FK | No | Must belong to the make; null = all models |
| vehicle_variant_id | FK | No | Must belong to the model; null = all variants |
| year_from | smallint | No | 1950–current+1; ≤ year_to when both set |
| year_to | smallint | No | Null = still current |
| engine_code | string(30) | No | Uppercase; e.g. `1GD-FTV`, `2KD-FTV` |
| notes | text | No | Fitment caveats shown at POS |
| source | enum | Auto | `tecdoc`, `supplier` (import-set), `manual` (user-set) |
| confirmed | boolean | Auto | Manual records start false; manager action sets true |

## Business Rules

1. At POS with a vehicle in context, confirmed fits are highlighted, unverified fits are flagged with "?", and known non-fits require an override reason to sell.
2. Multiple fitment records per part are expected (one part fits many vehicles); exact duplicates (same part + vehicle scope + engine) are rejected.
3. `tecdoc` and `supplier` records are read-only in the UI; staff corrections are made as `manual` records, which take display precedence over imported ones for the same vehicle scope.
4. A `manual` record shows as unverified until a manager confirms it; confirmation records who and when.
5. Deleting a fitment is allowed only for `manual` records; imported records are suppressed (hidden) instead, keeping the import re-runnable.
6. A wider record (all Hilux) and a narrower record (Hilux 2.8 GD-6 only) may coexist; the narrower record's notes win when both match the selected vehicle.
7. Re-running an import updates rows by external reference key; suppressed rows stay suppressed.
8. Fitment lookups must respect supersession: searching parts for a vehicle includes the superseding part when the superseded one carried the fitment.

## Edge Cases & Error Handling

- **Vehicle not in reference data** (grey import, rare variant): POS falls back to unfiltered search with a "no vehicle filter applied" banner; staff can request the vehicle be added to reference data.
- **Mid-year facelift changes the part** (Hilux pre/post-2011 differ despite same model year range): the `notes` field carries the caveat and the review queue encourages splitting into two records with month-accurate boundaries in notes.
- **Conflicting sources** (TecDoc says fits, supplier file says not): both display with source badges; manager resolves by adding a confirmed manual record, which outranks both.
- **Return reason "does not fit"** on a confirmed record: record is *not* auto-unconfirmed (the customer may have mis-stated the vehicle); a review task is raised with the sale's vehicle context attached.
- **Import file with unknown make/model codes**: unmatched rows land on an import exceptions report; nothing is silently dropped.
- **Engine code entered with inconsistent formatting** (`1gd ftv`): normalised to uppercase, spaces to hyphens, before duplicate checking.
- **Year_from after year_to** in a supplier file: row rejected to exceptions, not swapped silently.
