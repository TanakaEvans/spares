# 1.4 Stock Takes

> Full, cycle, and spot physical counts with variance review and posting. Part of [Module 1: Inventory Management](../01-inventory-management.md).

## Purpose

However disciplined the ledger, physical stock drifts from system stock: mis-picks (a `BRK-PAD-0122` sold but a `BRK-PAD-0123` handed over), unreported damage, theft, and supplier short-shipments all accumulate. Stock takes are the periodic reconciliation that pulls system quantities back to physical reality and quantifies shrinkage so management can act on it.

The sub-module supports three count styles matched to effort: an annual/half-yearly **full** count of the branch, a rolling **cycle** count where a slice of bins (e.g. aisle A this week) is counted weekly so the whole warehouse is covered each quarter without closing, and ad-hoc **spot** checks on specific parts when a discrepancy is suspected — typically raised automatically when a picker finds an empty bin the system says is stocked.

Accuracy depends on a controlled process: system quantities are frozen at the start for comparison, counters record blind counts (they do not see the expected figure), large variances force a recount by a second person, and nothing touches the ledger until a manager approves. Posting then flows through the standard adjustment mechanism, so the audit trail is identical to any other stock correction.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Storeman / Counter (staff) | Enter counts on sheets assigned to them; request recounts |
| Inventory Clerk | Create takes, print count sheets, enter counts |
| Inventory Manager | Freeze movements, review variances, approve and post; assign counters |
| Branch Manager | Approve takes with variance value above threshold |
| System Admin | Reopen a completed take (audit-logged); configure thresholds |

## Workflow

```
Create take (type: full/cycle/spot; scope: bins or parts)
        │
        ▼
Freeze system qtys (+ optionally freeze branch movements)
        │
        ▼
Print / assign count sheets per bin range
        │
        ▼
Count → enter counted qty (blind entry)
        │
        ▼
Variance review ──► variance > threshold? ──► mandatory recount (2nd counter)
        │                                          │
        ▼                                          ▼
Accept final qtys ◄────────────────────── recount_qty becomes final
        │
        ▼
Manager approves → Post (adjustment ledger entries) → notifications
```

1. Manager creates the take, choosing type and scope (whole branch, a bin range like `A-1-*` to `A-6-*`, or a part list for spot checks).
2. On start, `system_qty` is snapshotted per line; if `freeze_movements` is set, sales and GRN posting for the branch are blocked.
3. Count sheets are printed per bin (or loaded on a device by scanning the bin barcode); counters enter physical counts without seeing system figures.
4. The variance screen ranks lines by absolute variance value; lines over the recount threshold are flagged `recount_required` and assigned to a different counter.
5. Manager accepts final quantities line by line (or in bulk for zero-variance lines), approves, and posts. Posting writes `ADJUSTMENT_IN`/`ADJUSTMENT_OUT` ledger entries and stamps `last_counted_at` on stock levels.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Stock takes list | `inventory.stocktakes.index` | All takes with status, scope, variance summary |
| Stock take count | `inventory.stocktakes.count` | Line-by-line count entry per bin/sheet |
| Variance review | `inventory.stocktakes.review` | Ranked variances, recount flags, approve/post |

**Primary screen — Stock take count (`StockTakes/Count.jsx`):** Header shows take number, type, branch, status, and a progress bar (lines counted / total). A bin barcode scan box jumps to that bin's sheet. Main area lists the bin's expected parts — part number, description, bin, UoM — with a large numeric entry per line (system qty hidden while counting). "Add uncounted part" handles items found in the bin that the sheet did not expect. Footer actions: save progress, mark bin complete, next bin.

## Fields & Validation

Main form: count entry line.

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| counted_qty | decimal(10,2) | Yes | ≥ 0; decimals only for fractional UoM; blank ≠ zero (must be explicit) |
| recount_qty | decimal(10,2) | Cond. | Required when `recount_required`; entered by a different user than `counted_by` |
| final_qty | decimal(10,2) | Yes (at review) | Defaults to counted (or recount) qty; manager may override with note |
| counted_by | FK | Auto | Current user; must be an assigned counter for the sheet |
| notes | text | Cond. | Required when manager overrides final_qty manually |

Take header form: `type` (full/cycle/spot), `branch_id`, scope selector (bin range or part list — required for cycle/spot), `freeze_movements` (boolean, default true for full takes, false for cycle).

## Business Rules

1. `system_qty` is frozen at take start; movements after the freeze (when not locked) are listed on the review screen so the manager can judge whether a variance is real or timing.
2. With `freeze_movements` = true, POS sales, GRN posting, adjustments, and transfers for the branch are blocked until the take completes or is cancelled.
3. Variance above the recount threshold (configurable, e.g. > 5 units or > $200 line value) makes recount mandatory; the recount must be performed by a different user than the first count.
4. Count entry is blind: system quantities are hidden from counters and only revealed at variance review.
5. Posting creates a linked stock adjustment; the take itself never writes ledger rows directly.
6. A line left blank cannot be posted — every in-scope line needs an explicit count (zero is a valid count).
7. Only one active take may cover a given bin at a time; overlapping scopes are rejected at creation.
8. Serial-tracked parts are counted by scanning serials; the count is the number of serials scanned, and unexpected serials are flagged individually.
9. Accepted variances above the manager threshold require branch-manager approval; all accepted variances raise a management notification with total shrinkage value.

## Edge Cases & Error Handling

- **Sale happens mid-count on an unfrozen branch**: review screen shows the movement beside the variance; manager can adjust `final_qty` interpretation rather than posting a false shrinkage.
- **Part found in a bin it isn't assigned to**: "add uncounted part" records it against that bin; on posting, the system offers to create the overflow bin assignment.
- **Counter enters an implausible figure** (counted 400 where system expects 4): soft warning at entry ("10× expected — confirm?"), hard recount flag at review.
- **Take abandoned halfway** (e.g. delivery day chaos): manager cancels; freeze lifts, no ledger impact, entered counts retained read-only for reference.
- **Concurrent count entry on the same sheet** by two devices: line-level saves last-writer-wins with a visible "counted by" change log; bin completion locks the sheet.
- **Recount disagrees with both system and first count**: manager chooses the final quantity manually with a mandatory note.
- **Posting fails partway** (DB error): the whole post rolls back; take stays in `variance_review` and can be re-posted safely.
- **Frozen branch tries to invoice at POS**: cashier gets "branch frozen for stock take STK-2026-0021 — see manager", not a silent failure.
