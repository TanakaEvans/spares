# 1.8 Category Management

> The hierarchical parts categorisation tree with per-category GL, VAT, and display defaults. Part of [Module 1: Inventory Management](../01-inventory-management.md).

## Purpose

The category tree is how humans navigate ten thousand SKUs. A customer asks for "brake pads for a Hilux" — the counter drills Brakes → Brake Pads and filters by vehicle, rather than knowing a part number. The same tree drives the vehicle parts lookup, POS browse buttons, reporting rollups ("Brakes revenue up 12% this quarter"), and promotion targeting ("20% off everything under Filters").

Categories also carry financial defaults that keep bookkeeping consistent without per-part configuration: each category can define a default sales GL account, cost/COGS account, and VAT rate. When a part is created under Oils & Lubricants, its postings inherit the right accounts automatically; Finance changes a mapping once at category level instead of touching hundreds of parts.

The tree supports unlimited depth but the business standard is three levels — Main Group (Engine Parts, Brakes), Sub Group (Filters, Brake Pads), Detail Group (Oil Filters – Spin-on, Oil Filters – Cartridge). Deeper trees look organised but slow the counter down; this sub-module's job includes keeping the tree disciplined: merges for duplicates, controlled moves, and no orphaned parts.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Cashier / Counter | Browse tree at POS (read-only) |
| Inventory Clerk | Create categories, edit names/sort order, assign parts |
| Inventory Manager | Move/merge categories, deactivate, set defaults |
| Finance Manager | Edit GL account and VAT defaults per category |
| System Admin | Full access; bulk re-categorisation imports |

## Workflow

```
Plan structure (3-level standard)
        │
        ▼
Create main groups → sub groups → detail groups (code + name + sort order)
        │
        ▼
Finance sets per-category defaults (sales GL, COGS GL, VAT rate)
        │
        ▼
Parts assigned on creation / re-assigned in bulk
        │
        ▼
Ongoing maintenance:
   duplicate found ──► merge (parts move, loser deactivated)
   restructure     ──► move subtree (with impact preview)
   line dropped    ──► deactivate (only when empty of active parts)
```

1. Manager plans the structure; clerk creates nodes with a short `code` (e.g. `FILT-OIL`) used in reports and imports.
2. Finance sets GL/VAT defaults top-down; child categories inherit unless overridden.
3. Parts pick a category at creation ([1.1](1.1-parts-catalogue.md)); a bulk re-assign tool moves selections between categories.
4. Merging duplicates ("Oil Filter" vs "Oil Filters") re-points all parts and promotions to the survivor and deactivates the loser.
5. Moves of a subtree show an impact preview (part count, open promotions, report continuity note) before committing.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Categories | `inventory.categories.index` | Tree editor: create, rename, move, merge, deactivate |
| Category detail | `inventory.categories.show` | Parts in category, defaults, sub-tree stats |
| Bulk re-assign | `inventory.categories.reassign` | Move selected parts between categories |

**Primary screen — Categories (`Categories/Index.jsx`):** Header has search (matches name or code, expands the tree to hits), "New category", and an expand/collapse-all toggle. Main area is a drag-and-drop tree; each node shows name, code, part count (own + descendants), and status. Drag re-orders siblings (`sort_order`) or re-parents with a confirm dialog. Selecting a node opens a right-hand panel with its fields, financial defaults (with "inherited from Engine Parts" indicators), and actions: merge into…, deactivate, view parts.

## Fields & Validation

Main form: category.

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| name | string(100) | Yes | Unique among siblings (case-insensitive) |
| code | string(20) | Yes | Unique tree-wide; uppercase; `[A-Z0-9\-]+` |
| parent_id | FK | No | Null = top level; cannot be self or own descendant |
| sort_order | int | Yes | Auto-assigned on create; drag-editable |
| is_active | boolean | Yes | Deactivation gated by rules below |
| default_sales_gl_id | FK | No | Active GL account; inherits from parent when null |
| default_cogs_gl_id | FK | No | Active GL account; inherits when null |
| default_vat_rate_id | FK | No | Active VAT rate; inherits when null |
| show_in_pos_browse | boolean | Yes | Whether the node appears as a POS browse tile |

## Business Rules

1. Category names must be unique among siblings; codes unique across the whole tree.
2. Re-parenting cannot create a cycle — a node can never be moved under its own descendant.
3. Tree depth is soft-limited to 3 levels: creating level 4 warns and requires manager confirmation.
4. A category cannot be deactivated while it (or any descendant) contains active parts or is targeted by an active promotion.
5. Financial defaults resolve by walking up the tree: part's category → nearest ancestor with a value → system default. Changing a default affects future postings only, never posted history.
6. Merging categories re-points parts, fitment lookups, and promotion lines to the survivor in one transaction; the merged-away node is deactivated and records what it merged into.
7. Parts may carry additional categories via tags ([1.1](1.1-parts-catalogue.md)), but exactly one primary `category_id` drives GL/VAT defaults.
8. Deleting a category outright is only possible when it never had parts or postings; otherwise deactivate.
9. Report rollups always aggregate by the current tree; a "category history" audit log records moves/merges so period comparisons can be footnoted.

## Edge Cases & Error Handling

- **Two clerks create "Wheel Bearings" under different parents**: sibling-uniqueness doesn't catch it; a periodic duplicate-name report surfaces cross-parent duplicates for merge review.
- **Move of a subtree with an active promotion targeting it** ("20% off Filters"): impact preview lists the promotion; the move proceeds but the promotion keeps targeting the moved node (it follows the id, not the path).
- **VAT default changed mid-day** (rate policy change): open drafts re-resolve on posting; already-posted documents are untouched — corrections go through credit notes.
- **Category with 4,000 parts merged on a busy afternoon**: merge runs as a queued job with progress; parts remain sellable throughout (only the label changes).
- **Import references a category code that was merged away**: import maps via the merge-forwarding record to the survivor and notes the mapping on the import report.
- **Drag-and-drop mis-drop** (Brake Pads dropped under Electrical): confirm dialog states old and new parent before committing; a single-step "undo move" is available for 5 minutes.
- **Deactivation attempted on "Brakes"** while Brake Pads still has parts: blocked with a drill-down list of blocking descendants.
- **POS browse tiles overflow** (too many level-1 nodes flagged): `show_in_pos_browse` limit warns beyond 12 tiles to keep the POS grid usable.
