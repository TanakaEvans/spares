# 8.1 Vehicle Makes

> Master list of every vehicle brand the business sells parts for. Part of [Module 8: Vehicle & Parts Reference](../08-vehicle-parts-reference.md).

## Purpose

Vehicle Makes is the top level of the vehicle hierarchy (Make → Model → Variant). Every fitment record, every customer vehicle, and every engine code ultimately hangs off a make record, so this list must be clean, de-duplicated, and consistently coded before any other reference data is loaded.

For a Southern/Central African spares business the make list is not academic — it drives the counter workflow. When a customer says "it's for a Nissan NP300", the cashier's first click is the make. A make list polluted with duplicates ("VW" and "Volkswagen" as separate rows) fragments fitment data and produces wrong "no parts found" answers, which directly loses sales.

The `sort_order` column exists because market prevalence matters: Toyota and Nissan should appear at the top of every dropdown, not alphabetically buried below BAIC and BYD. Seeding follows the prioritised list in the parent module doc (Toyota first, then Nissan, Ford, Volkswagen, and the growing Chinese brands such as Chery and Haval/GWM).

## Workflow

```
[Need new make] → [Check for existing/near-duplicate] → [Create make]
      │                                                      │
      │                                                      ▼
      │                                          [Set code + sort order]
      │                                                      │
      ▼                                                      ▼
[Bulk import (CSV / CarQuery / NHTSA)] ──────────► [Activate → available
                                                    in model & fitment UIs]
```

1. **Duplicate check** — before creating, search by name and code. The system warns on close matches (e.g. "Landrover" vs "Land Rover", "Mercedes" vs "Mercedes-Benz").
2. **Create** — capture name, 2–10 character code (e.g. `TOY`, `NIS`), country of origin, optional logo.
3. **Order** — assign `sort_order`; popular African-market makes get low numbers so they surface first at POS.
4. **Bulk import** — CSV upload or API pull (CarQuery / NHTSA) for the initial seed; importer skips rows whose name or code already exists.
5. **Activate/deactivate** — deactivating hides the make from new-data dropdowns but keeps history intact.

## Fields & Validation

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| name | text | Yes | max 100; unique (case-insensitive) |
| code | text | Yes | 2–10 chars; uppercase alpha; unique |
| country_of_origin | text | No | max 100 |
| logo_path | image upload | No | png/jpg/svg, max 1 MB, stored via Laravel storage |
| sort_order | integer | No | >= 0; defaults to max + 10 |
| is_active | boolean | Yes | defaults true |

## Business Rules

1. Make names are unique case-insensitively; "TOYOTA" and "Toyota" are the same make.
2. Codes are immutable once the make has models — changing a code would break document references and export files.
3. A make cannot be deleted if any `vehicle_models`, `engine_codes`, or `customer_vehicles` reference it; it can only be deactivated.
4. Deactivating a make hides it from create-flows (new models, new customer vehicles, POS make filter) but existing fitments and history keep working.
5. Sub-brands are separate makes when the market treats them separately (Datsun is listed under Nissan per the seed list, but GWM and Haval share one entry "Haval/GWM" — follow the seed list convention).
6. Bulk import is additive only: it never updates or deletes existing makes, and it reports skipped duplicates.
7. Logos are optional but, when present, print on fitment lookup screens only — never on financial documents.

## Edge Cases & Error Handling

- **Rebranded manufacturer** (e.g. Datsun retired by Nissan): keep the old make active while customer vehicles reference it; new models go under the successor make.
- **Merged duplicates**: if "VW" and "Volkswagen" both accumulated data, an admin merge tool re-points models/vehicles to the survivor and deactivates the loser; the merge is written to the activity log.
- **Import file with mixed encodings** (e.g. "Citroën"): importer normalises to UTF-8 and flags rows it cannot decode rather than silently corrupting names.
- **Deleting a make with data**: blocked with a message listing the dependent counts ("14 models, 210 customer vehicles reference this make").
- **Code collision on import**: row is skipped and listed in the post-import report with the conflicting existing make.
- **Logo upload failure** (oversize/wrong type): form error on the logo field only; the rest of the make record still saves if the user removes the file.
