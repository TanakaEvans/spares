# 8.2 Vehicle Models & Variants

> Models and their engine/trim variants — the level fitment data actually attaches to. Part of [Module 8: Vehicle & Parts Reference](../08-vehicle-parts-reference.md).

## Purpose

A "Toyota Hilux" is not one vehicle for parts purposes. A 2.4 GD-6 (engine 2GD-FTV) takes different filters, injectors, and glow plugs than a 2.8 GD-6 (1GD-FTV), and the 2020 facelift changed brake and lighting components again. This sub-module captures models (Hilux, NP300, Ranger) and beneath them variants — the specific engine, transmission, drive, and year-range combinations that determine which parts fit.

Variants are the precision layer of the whole reference module. Fitment records ([8.4](8.4-fitment-guide.md)) point at variants, not models, wherever possible; a fitment attached only at model level is inherently a "verify" confidence answer. Getting variant data right is what turns a counter conversation from "should fit, bring it back if not" into "confirmed fit", which cuts the returns rate measured in [Module 9 Returns Analysis](../09-reports-analytics.md#92-sales-reports).

Year ranges matter as much as engines. The business sells into a market full of grey imports and long-lived bakkies, so `year_from`/`year_to` and `market_region` (a `southern_africa` variant may differ from the `europe` one) must be captured, not guessed.

## Workflow

```
[Select make] → [Create model] → [Add variants under model]
                    │                     │
                    ▼                     ▼
        [Set body type, segment,   [Engine code, cc, fuel,
         year range, generation]    power, transmission,
                                    drive, years, region]
                                          │
                                          ▼
                              [Variant available for fitment
                               records & customer vehicles]
```

1. **Create the model** under its make with body type, segment, generation label, and production year range.
2. **Add variants** — one per distinct engine/trim/drive/years combination. Naming convention: displacement + engine badge + trim + drive + transmission, e.g. "2.8 GD-6 Legend 4×4 AT".
3. **Link engine code** — variant's `engine_code` should match a record in [8.5 Engine Codes](8.5-engine-codes.md); the form offers autocomplete from that table.
4. **Split on facelifts** — when a facelift changes mechanical spec (Hilux 1GD-FTV went 150 kW → 165 kW in 2020), create a second variant with the new year range rather than editing the old one.
5. **Consume downstream** — fitment records, customer vehicles, and workshop job cards select variants from this list.

**Primary screen — Variants list** (`VehicleRef/Variants/Index.jsx`): left panel is a make → model tree; right panel lists the selected model's variants as rows showing name, engine code, cc, fuel, kW, drive, transmission, and year range (e.g. `2.4 GD-6 Raider 4×4 MT | 2GD-FTV | 2393cc | diesel | 110kW | 2016–2020`). Row actions: edit, duplicate (pre-fills a copy — the fastest way to enter facelift variants), deactivate.

## Fields & Validation

Variant form (the model form is a subset — name, body_type, segment, years, generation):

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| model_id | select | Yes | must exist and be active |
| name | text | Yes | max 150; unique within model + year range |
| engine_code | autocomplete | No | max 30; warn if not found in `engine_codes` |
| engine_size_cc | integer | No | 50–20000 |
| fuel_type | select | Yes | one of petrol/diesel/hybrid/electric/lpg |
| power_kw / power_hp | integer | No | > 0; if both given, hp ≈ kW × 1.341 ± 5% or warn |
| cylinders | integer | No | 1–16 |
| aspiration | select | No | naturally_aspirated/turbo/supercharged |
| transmission | select | No | manual/automatic/cvt/amt |
| drive | select | No | 4x2/4x4/awd/fwd/rwd |
| year_from | integer | Yes | 1950–current year + 1 |
| year_to | integer | No | >= year_from; null = still in production |
| market_region | select | No | defaults `global` |

## Business Rules

1. A variant's year range must fall within its model's year range; the form blocks a 2014 variant under a model that started in 2015.
2. Facelift/spec changes create a new variant; existing variants are never retro-edited once fitments reference them, because that would silently corrupt fitment answers.
3. Deleting a model or variant is blocked while `part_fitments` or `customer_vehicles` reference it — deactivate instead.
4. `year_to = null` means "current"; reports and dropdowns display it as "current" not blank.
5. Variants with an `engine_code` not present in the engine codes table are allowed (data arrives incomplete) but are flagged on a data-quality widget until resolved.
6. Duplicate detection: same model + same engine_code + overlapping years + same drive/transmission raises a warning before save.
7. `market_region` defaults to `global`; region-specific variants (e.g. a Euro-only engine) should never be offered in POS fitment filtering when a `southern_africa` sibling exists for the same years.

## Edge Cases & Error Handling

- **Grey imports** (JDM Hiace, UK-spec vehicles): create variants with the appropriate `market_region`; fitment confidence for these shows "~ Likely" unless explicitly confirmed.
- **Mid-year running changes** (VIN-break rather than year-break): capture the detail in a [technical bulletin](8.7-technical-bulletins.md) and split variants at the nearest year; the bulletin warns staff to check VIN.
- **Customer knows only "Hilux 2019"**: POS fitment lookup accepts model + year and returns parts fitting *any* matching variant, marked "? Verify" where variants disagree.
- **Chassis/badge overlap** (Nissan NP300 Hardbody vs Navara-based NP300): keep them as separate models with clear generation labels so counter staff cannot pick the wrong platform.
- **Variant deactivated while a job card references it**: the job card keeps its snapshot; only new selections are prevented.
- **Conflicting power figures across sources**: store the manufacturer figure, note alternatives in a variant note; never average.
