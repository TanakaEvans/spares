# 8.6 Supersession Management

> Handles manufacturer part-number changes so old numbers always resolve to the current part. Part of [Module 8: Vehicle & Parts Reference](../08-vehicle-parts-reference.md).

## Purpose

Manufacturers routinely discontinue a part number and replace it with a new one — a revised design, a consolidated SKU, or a packaging change. Customers, old invoices, printed catalogues, and suppliers' systems keep quoting the old number for years afterwards. Supersession management guarantees that searching any number in a chain lands on the *current, orderable* part, while preserving the old records for sales history, warranty lookups, and stock that may still sit on the shelf under the old number.

Without it, every supersession becomes a lost-sale trap ("that number doesn't exist") or a duplicate-stock trap (the same physical part stocked twice under old and new numbers, each showing half the true availability). Chains matter too: after several revisions a number may be three hops from current (`A → B → C`), and staff should never have to walk that chain manually.

Supersessions also protect purchasing: a PO raised against a superseded number is caught at entry, before the supplier ships the replacement and the GRN mismatches.

## Workflow

```
[Supplier notice / catalogue update: 90915-30002 replaced by 90915-YZZD3]
                          │
                          ▼
            [Record supersession: old → new]
                          │
          ┌───────────────┼────────────────────┐
          ▼               ▼                    ▼
 [Old part flagged   [Searches for old   [Remaining old stock
  "superseded";       number redirect     sell-through plan:
  blocked on new      to new part with    sell out first or
  POs]                amber notice]       return to supplier]
                          │
                          ▼
        [Chain check: if old was itself a target
         (X → old), chain becomes X → old → new
         and X now resolves to new]
```

1. **Detect** — supersession news arrives via supplier notices, TecDoc updates, or a failed order ("that number is replaced").
2. **Record** — data admin links old part → new part with an effective date and source.
3. **Redirect** — all lookups ([cross-ref](8.3-parts-cross-reference.md), fitment, POS search) resolve the chain to its end and show a notice.
4. **Sell through** — existing stock under the old number remains sellable; POS shows "superseded — old stock, sell first" so it drains before the new SKU.
5. **Restrict purchasing** — new POs on a superseded part are blocked (or warned, per settings) and offered the replacement instead.

| Supersessions list | `vehicle-ref.supersessions.index` | All chains, searchable by either number |
| Record supersession | `vehicle-ref.supersessions.create` | Link old → new |
| Chain viewer | `vehicle-ref.supersessions.show` | Visualise a full chain with stock at each hop |

**Primary screen — Supersessions list**: table of old part, new part, effective date, source, chain depth, and remaining stock on the old number. A "Chain" link expands the full path (`90915-20003 → 90915-30002 → 90915-YZZD3`) with on-hand and last-sold at each hop, so the buyer can see how much legacy stock still needs draining.

## Fields & Validation

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| old_part_id | part search | Yes | must exist; cannot equal new_part_id |
| new_part_id | part search | Yes | must exist and be active |
| effective_date | date | Yes | not more than 30 days in the future |
| source | text | No | max 100, e.g. "Toyota SA bulletin Mar 2026" |
| notes | text | No | e.g. "New number includes revised O-ring — interchangeable both ways" |
| interchangeable | boolean | Yes | default true; false = new part does NOT retrofit older applications |

## Business Rules

1. Chains resolve automatically: any search for a superseded number returns the final active part in the chain, with the notice naming the hop count.
2. Circular chains are impossible — the validator rejects any link that would create a cycle (A → B → A).
3. An old part cannot have two forward links; a supersession is one-to-one. One-to-many replacements ("kit split into two parts") are handled as a discontinuation plus a [technical bulletin](8.7-technical-bulletins.md), not a supersession.
4. The old part record is never deleted: sales history, warranty claims, and shelf stock still reference it.
5. Old-number stock remains sellable until zero; POS prefers old stock when both old and new are on hand (configurable), so capital is not stranded.
6. New purchase orders against a superseded part are blocked with the replacement suggested; receiving (GRN) against an already-issued PO for the old number is still allowed.
7. Fitment records on the old part are inherited by the chain end for search purposes — the [Fitment Guide](8.4-fitment-guide.md) shows the current part with the old part's applications.
8. If `interchangeable = false`, the redirect notice escalates to a warning and confidence in fitment results is capped at ? Verify for older applications.

## Edge Cases & Error Handling

- **Chain end is itself later superseded**: recording C → D silently extends every chain terminating in C; the resolver always walks to the live end at query time.
- **Supersession recorded, then reversed by manufacturer** (it happens): the link can be end-dated/removed by an admin; removal is activity-logged and both parts revert to independent SKUs.
- **Both parts have stock and different prices**: POS notice shows both prices; selling the old stock at the new price (or vice versa) is a pricing decision surfaced, never silently applied.
- **Customer returns a part bought under the old number after the chain moved on**: return is processed against the original invoice line and old part; restocking puts it back on the old SKU.
- **Import feeds a supersession for parts not in the catalogue**: held in an exception list; the chain is only created once both ends exist as parts.
- **Deep chains (4+ hops)**: fully supported, but the chain viewer flags them for consolidation review since deep chains usually mean stale catalogue data.
