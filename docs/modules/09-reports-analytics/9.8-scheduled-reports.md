# 9.8 Scheduled Reports

> Automated generation and email delivery of reports on a schedule — no manual action required. Part of [Module 9: Reports & Analytics](../09-reports-analytics.md).

## Purpose

Reports that must be pulled don't get read. Scheduled Reports pushes them: the branch manager's Daily Sales Summary lands at 08:00, the buyer's Stock Reorder list every Monday at 07:00, the owner's P&L on the 3rd of the month — as PDF or Excel attachments, generated and emailed by the scheduler with no one clicking anything.

Any report in the module that supports parameterised running can be scheduled. A schedule is a saved configuration: which report (`report_key`), how often, at what time, with which parameters (date-range expressions like "yesterday" or "last month", branch filters), to which recipients, in which format. The default set from the parent doc seeds seven schedules covering sales, stock, ageing, P&L, top customers, and dormant customers.

Reliability and confidentiality are the design constraints: a silently failed schedule means a manager operating blind, and a mis-addressed P&L is a serious leak — hence run logging and recipient controls.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Super Admin | Full CRUD on all schedules |
| Owner / Accountant | Create/edit schedules for reports they can view |
| Branch Manager | Create schedules for own-branch reports; recipients within the company |
| Sales / Purchasing managers | Schedules for their report areas |
| All others | Receive emails only; no schedule management |

## Workflow

```
[Create schedule: report + frequency + time + parameters
 + recipients + format]
                    │
                    ▼
     [Laravel scheduler tick (every minute)]
                    │
                    ▼
   [Due? → queue report-generation job]
                    │
                    ▼
 [Resolve relative parameters ("yesterday",
  "last month") → run report → render PDF/Excel]
                    │
          ┌─────────┴──────────┐
          ▼                    ▼
   [Email to recipients   [Failure → retry ×3,
    with attachment;       then alert admin +
    stamp last_run_at]     mark run failed]
```

1. **Configure** — pick the report, frequency (`daily`/`weekly`/`monthly`), run time, run day (1–7 weekly, 1–31 monthly), parameters, recipients, format (`pdf`/`excel`).
2. **Dispatch** — the scheduler compares due times against `last_run_at` and queues due schedules; generation runs on the queue, never in a web request.
3. **Resolve dates** — parameters store relative expressions resolved at run time, so "yesterday" is always yesterday.
4. **Deliver** — email sent via the configured mailer ([10.11 Email Configuration](../10-system-administration/10.11-email-configuration.md)) using the scheduled-report template, attachment named `{report}-{date}.{ext}`.
5. **Log** — every run recorded with status, duration, and recipients; failures retry then alert.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Scheduled reports list | `reports.scheduled.index` | All schedules with status and last run (`Reports/Scheduled/Index.jsx`) |
| Schedule create/edit | `reports.scheduled.create` / `.edit` | Configuration form |
| Run history | `reports.scheduled.index` (row expand) | Per-schedule run log |

**Primary screen — Scheduled reports list**: table of name, report, frequency ("Daily 08:00", "Monthly, 3rd"), recipients count, format, active toggle, last run (timestamp + status dot), next run. Row actions: edit, "Run now" (manual trigger for testing), view run history. Failed last runs highlight the row.

## Fields & Validation

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| name | text | Yes | max 100 |
| report_key | select | Yes | must be a schedulable report the creator can view |
| frequency | select | Yes | daily / weekly / monthly |
| run_time | time | Yes | valid time, company timezone |
| run_day | integer | Weekly/monthly | 1–7 (weekly), 1–31 (monthly) |
| parameters | dynamic form | Per report | validated against the report's own filter rules; date ranges as relative expressions |
| recipients | email list | Yes | >= 1 valid address; warning for addresses outside known users/company domain |
| format | select | Yes | pdf / excel |
| is_active | boolean | Yes | default true |

## Business Rules

1. A user can only schedule reports they are themselves permitted to view, at their own branch scope — scheduling is not a permission bypass.
2. Recipients receive exactly what the schedule's *creator* could see; if the creator loses the underlying permission, the schedule suspends rather than leaking.
3. Relative date expressions resolve at run time in the company timezone.
4. `run_day` 29–31 in short months executes on the last day of the month instead of skipping.
5. Missed runs (server down at run time) execute once on recovery within a grace window (e.g. 6 hours); older misses are logged as skipped, never bulk-replayed.
6. Reports render with the same code paths as the on-screen versions — a scheduled Daily Sales Summary always matches what the screen showed for that day.
7. Failure handling: 3 retries with backoff, then the run is marked failed and an admin alert email is sent; the schedule stays active.
8. Deactivating a schedule preserves it and its history; deleting requires confirmation and keeps run-log rows for audit.
9. Empty results still send (a zero-sales day is information); the email body notes "no data for this period".

## Edge Cases & Error Handling

- **Recipient mailbox bounces**: bounce recorded against the run; repeated bounces flag the recipient on the schedule for cleanup.
- **Report generation exceeds queue timeout** (huge dataset): job splits export to a stored file and emails a download link instead of an oversized attachment; attachments are capped (e.g. 10 MB).
- **Schedule owner leaves the company**: deactivating the user suspends their schedules with an admin notification listing them for reassignment.
- **Two schedules due in the same minute**: queue workers process them independently; one failing never blocks the other.
- **Parameter referencing a deleted branch/customer**: run fails validation with a clear reason in the run log rather than emailing a wrong-scope report.
- **DST/timezone shifts**: run times follow the company timezone; a skipped/doubled wall-clock hour resolves to a single run.
- **"Run now" testing**: manual trigger delivers only to the person triggering (or a test address), not the full recipient list, unless explicitly confirmed.
