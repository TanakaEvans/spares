# 5.5 Statements

> Monthly account statements for trade customers — the document the garage pays from. Part of [Module 5: Customer Management](../05-customer-management.md).

## Purpose

For trade customers, the monthly statement is the primary payment trigger. Most garages and fleets do not pay invoice-by-invoice; their bookkeeper reconciles the month-end statement against their own records and pays the closing balance (or the "current + 30" portion). If the statement is late, wrong, or missing invoices, payment slips a month — so statement accuracy and on-time delivery directly drive cash flow.

A statement is a period snapshot of the account: opening balance, every invoice and credit note issued, every receipt received and any discounts or interest applied, closing balance, and an aged analysis so the customer sees exactly which portion is overdue. It is a *report over AR data*, not a source document — nothing posts from a statement; it reflects what AR ([7.3](../07-finance-accounts/7.3-accounts-receivable.md)) already recorded.

The system automates the whole cycle: on the 1st of each month it generates statements for every trade customer with a balance or movement, renders PDFs, and emails them to the statement contact(s), with print fallback for customers without email. Ad-hoc statements can be produced any time for any date range — a garage phoning to query their account gets an up-to-the-minute statement while on the call.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Accounts Clerk | Generate/regenerate/print/email statements; maintain delivery contacts |
| Credit Controller | Run the monthly batch; view delivery failures; annotate statements |
| Counter Sales | Print current statement for a customer at their request |
| Branch Manager | View all; approve statement message/banner text |
| Customer (external) | Receives PDF by email; no system access |

## Workflow

Main process: automated month-end statement run.

```
1st of month, 06:00 (scheduled job)
        │
Select trade customers with movement OR balance ≠ 0 in prior month
        │
For each: build statement (opening bal → transactions → closing bal → ageing)
        │
Render PDF ──> store against customer + period
        │
Delivery routing:
  email contact(s) exist ──> queue email with PDF attached
  no email             ──> add to print queue
        │
Delivery log updated (sent / bounced / printed)
        │
Exceptions report to Credit Controller (bounces, zero-contact accounts)
```

1. **Selection.** All customers with `credit_limit > 0` or non-zero balance, plus any account with movement in the period — including COD trade accounts that transacted.
2. **Build.** Opening balance = prior statement's closing balance; the run verifies this equals (closing balance recomputed from all history) and flags mismatches instead of sending.
3. **Render.** PDF on company letterhead: transactions in date order with document numbers, payments and allocations, ageing footer, banking details, and remittance advice slip.
4. **Deliver.** Email to every contact with `receives_statements = true`; bounces are logged and retried once; persistent failures go to the exceptions list.
5. **Archive.** Every generated statement PDF is stored immutably per customer per period — what the customer received can always be reproduced exactly.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Account statement | `customers.statement` | View/print/email a statement for a customer + period |
| Statement run dashboard | via `customers.credit` | Batch status, delivery log, exceptions |
| Customer profile — Statements tab | `customers.show` | Archive of past statements for one customer |

**Primary screen — Account statement (`customers.statement`):**
- **Header:** customer name and number, statement period selector, closing balance, delivery status of the archived copy.
- **Main area:** statement preview exactly as the PDF renders — opening balance, dated transaction lines (invoices, credit notes, receipts, interest, discounts), closing balance, aged analysis strip (Current / 30 / 60 / 90+).
- **Actions:** Email Now, Download PDF, Print, Regenerate (Accounts Clerk+), Change Period.

## Fields & Validation

Statement generation / delivery settings:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| Statement period | month select | Yes | Any closed or current month; future months blocked |
| Custom date range | date pair | No | start ≤ end; ad-hoc statements only, watermarked "INTERIM" |
| Delivery method | select | Yes | `email`, `print`, `both`; email requires ≥ 1 contact with valid email and `receives_statements = true` |
| Statement contacts | multi-select | Email only | From `customer_contacts`; RFC-valid email each |
| Statement message | text(500) | No | Batch-level banner (e.g. "Note new banking details"); Branch Manager approval required |
| Include zero-balance | boolean | No | Default off for batch; on for ad-hoc |

## Business Rules

1. Statements are generated for all trade customers with a balance **or** movement in the period (expands parent rule: zero-balance accounts with movement still get one — the customer needs to see the account was settled).
2. Opening balance must equal the prior period's closing balance; any mismatch (caused by back-dated postings) blocks that customer's statement and raises an exception rather than sending a wrong document.
3. Back-dated transactions posted after a statement was sent appear on the **next** statement as prior-period items, clearly dated — archived statements are never silently regenerated.
4. `Regenerate` creates a new version; all versions are retained with generation timestamp and user, and the delivery log records which version was sent.
5. The aged analysis on the statement uses the same due-date-based buckets as Credit Management (5.3) — one ageing truth, two surfaces.
6. Interest/penalty lines (from 5.2 penalty runs) and early-settlement discount credit notes appear as ordinary dated transactions with their journal references.
7. Statement emails send from a no-reply address with reply-to set to the accounts department; every send is logged with message ID for dispute resolution ("we never got a statement").
8. Ad-hoc mid-month statements are watermarked INTERIM and excluded from the official archive sequence.

## Edge Cases & Error Handling

- **Email bounces for the only statement contact:** the account lands on the exceptions list; the clerk phones (logging the call in 5.8), fixes the address, and re-sends — the fix updates `customer_contacts` so next month works.
- **Customer disputes an invoice on the statement:** the dispute flag (5.3) does not alter the statement — the invoice still appears — but disputed items are marked with an asterisk and footnote so the customer knows it is acknowledged.
- **Receipt allocated to the wrong invoice after the statement went out:** reallocation (7.3) changes ageing but not the closing balance; the next statement's ageing simply reflects the correction — no restatement needed.
- **Statement run overlaps period close:** the run reads AR as at the period boundary snapshot; postings racing the run are cut off at the period end date and fall into next month's statement.
- **Customer on hold / blacklisted:** statements still generate and send — collections needs the paper trail most for exactly these accounts.
- **Printer queue for no-email customers forgotten:** the run dashboard shows unprinted count ≥ 1 as a red badge until cleared; unprinted statements older than 3 business days escalate to the Credit Controller.
- **Huge fleet statement (500+ lines):** PDF paginates with per-page running balances; email attachments over the mail size limit switch to a secure download link automatically.

## Key Tables

- Statement header/version and delivery-log tables — one row per customer per period per version, with archived PDF reference.
- `customers`, `customer_contacts` — balance and delivery routing (see 5.1).
- Source transactions: sales documents, credit notes, `customer_receipts`, `receipt_allocations` — owned by Sales and [7.3 Accounts Receivable](../07-finance-accounts/7.3-accounts-receivable.md); statements only read them.
