# 5.7 Customer Groups

> Segments customers so pricing, terms, and marketing rules apply by type, not one-by-one. Part of [Module 5: Customer Management](../05-customer-management.md).

## Purpose

A spares business does not price customer-by-customer — it prices by segment. Retail walk-ins pay list price; mechanics get trade price (typically list − 15–25%); panel beaters get trade price on body panels but retail on service parts; fleets negotiate contract pricing; dealers buy at near-wholesale. Customer groups encode these segments once, so that assigning a new garage to the "Mechanics" group instantly gives it the right price list, default discount, starting credit limit, and payment terms — no per-customer configuration, no counter-staff discretion.

Groups are also the levers for commercial policy changes. When the business decides mechanics move from Net 30 to Net 45, or the fleet discount changes from 5% to 7%, the change is made on the group and rolled out deliberately to members, rather than edited across hundreds of profiles. And because sales reporting slices by group, management can answer "what margin do we make on panel beaters vs. fleets?" directly.

Finally, groups gate programme eligibility: the loyalty programme (5.6) applies to retail groups only, and marketing campaigns target groups (e.g. a brake-pad promotion emailed to Mechanics only).

## User Roles & Permissions

| Role | Access |
|------|--------|
| System Admin | Create/edit/deactivate groups; change group defaults |
| Financial Manager | Approve changes to default discount, credit limit, or terms |
| Branch Manager | Assign customers to groups; request group changes |
| Sales Rep | View groups; propose reassignment for portfolio customers |
| Counter Sales | Sees the effect (pricing/terms) only; no group visibility needed |

## Workflow

Main process: creating a group and rolling out a defaults change.

```
Create group ──> name, description
        │
Set defaults: price list, discount %, credit limit, payment terms
        │
Financial Manager approval (commercial defaults)
        │
Group active ──> new customers assigned inherit defaults
        │
─── later: defaults changed on group ───
        │
System asks: apply to existing members?
   ├─ "New members only"  ──> existing customers untouched
   └─ "Re-apply to members" ──> preview list of affected customers
              │                   (overridden customers highlighted)
              ▼
      Confirm ──> defaults pushed; per-customer overrides preserved
                  unless "reset overrides" explicitly ticked
```

1. **Define.** Admin creates the group with a clear name matching the trade segment ("Retail", "Mechanics", "Fleet", "Panel Beaters", "Dealers").
2. **Set defaults.** Price list, discount %, starting credit limit, payment terms. These are *defaults for new members*, not live links — the values copy onto the customer at assignment.
3. **Approve.** Commercial defaults require Financial Manager approval before the group can be used.
4. **Assign members.** At customer creation (5.1) the group is mandatory; reassignment later re-prompts for defaults application.
5. **Roll out changes.** Group edits offer a controlled push to existing members with a preview and explicit handling of customer-level overrides.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Customer groups | `customers.groups.index` | List of groups with member counts and defaults |
| Group detail/edit | within `customers.groups.index` | Defaults, members list, change history |
| Bulk reassignment | within `customers.groups.index` | Move selected customers between groups |

**Primary screen — Customer groups (`customers.groups.index`):**
- **Header:** group count, total customers, "New Group" button (Admin).
- **Main area:** table — group name, member count, default price list, default discount %, default terms, default credit limit, status; expanding a row shows recent members and the change history.
- **Actions:** New Group, Edit Defaults (approval-gated), Deactivate, View Members, Bulk Reassign, Export Members.

## Fields & Validation

Group create/edit form:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| Name | text(100) | Yes | Unique among active groups |
| Description | textarea | No | Max 1000 chars |
| Default price list | FK select | Yes | Active price list (Inventory/Pricing) |
| Default discount % | decimal(5,2) | Yes | 0–50; > 25 requires Financial Manager approval note |
| Default credit limit | decimal(15,2) | Yes | ≥ 0; 0 = new members start cash-only |
| Default payment terms | FK select | Yes | Active `payment_terms`; credit-bearing terms require default limit > 0 or explicit confirmation |
| Loyalty eligible | boolean | Yes | Only groups with retail-type membership may enable (see 5.6) |
| Status | select | Yes | `active` / `inactive`; inactive blocks new assignment only |

## Business Rules

1. Every customer belongs to exactly one group; group is mandatory at creation (5.1).
2. Group defaults are **copied** to the customer at assignment, not referenced live — subsequent group edits change nothing on members unless explicitly rolled out (expands the parent doc: prevents an accidental group edit from re-pricing the whole book instantly).
3. Rolling out a defaults change preserves customer-level overrides by default; resetting overrides is a separate, explicit checkbox with its own preview.
4. Discount stacking: the group discount and any customer-specific discount do not stack — the customer-level value, when present, replaces the group value.
5. A group cannot be deleted while it has members (active or inactive); deactivation is the supported path.
6. Moving a customer between groups triggers the same defaults prompt as a rollout ("keep current commercial settings" vs. "adopt new group defaults") and requires Branch Manager permission because it can change pricing.
7. Credit-relevant defaults (limit, terms) applied via group rollout still respect the Credit Management approval thresholds (5.3) — a rollout cannot silently grant limits above the approver's authority; such members drop to an approval queue.
8. Group change history (who changed which default, old → new, rollout scope) is retained indefinitely.

## Edge Cases & Error Handling

- **Customer is in "Mechanics" but negotiated fleet-level pricing:** the per-customer price-list override (5.1) wins; the group's rollout preview highlights the customer as "overridden — will be skipped".
- **Group discount raised to 30% by mistake and rolled out:** the rollout preview shows margin impact per price list before confirm; post-hoc, the change history enables a reverse rollout to the prior values.
- **Bulk reassignment includes on-hold customers:** allowed — group affects pricing/terms defaults, not the hold; the preview flags them so the operator is aware terms changes will not lift holds.
- **Loyalty enabled on a trade group:** blocked by validation (rule: only retail-type groups) — prevents trade accounts quietly earning points against rule 1 of 5.6.
- **Two branches want different mechanic pricing:** groups are company-wide; branch-differentiated pricing belongs in price lists (branch-specific price lists assigned to the same group's members per branch), not in duplicate groups — the UI guidance note says so on group creation.
- **Deactivated group still assigned to hundreds of customers:** fully supported; members keep functioning, the group just stops accepting new members and shows an "inactive" badge wherever displayed.
- **Rollout interrupted halfway (server restart):** rollouts run as a tracked batch job with per-member status; resume completes the remainder, and no member is applied twice.

## Key Tables

- `customer_groups` — group master: name, defaults (schema in [Module 5](../05-customer-management.md#57-customer-groups)).
