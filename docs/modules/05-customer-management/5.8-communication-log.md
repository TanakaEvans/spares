# 5.8 Communication Log

> Every call, email, visit, note, and complaint per customer — one timeline, no tribal knowledge. Part of [Module 5: Customer Management](../05-customer-management.md).

## Purpose

In a trade business, relationships live in conversations: the garage owner who was promised a call-back about a warranty claim, the fleet manager who complained about a short delivery, the mechanic who said "I'll settle Friday". If those conversations live in one salesperson's head, the business is exposed — staff leave, promises get forgotten, and the Credit Controller phones a customer who was promised something different yesterday. The communication log makes every interaction a record on the customer timeline, visible to anyone opening the profile.

The log serves three distinct users. Sales reps record visits and calls so account handover is possible and managers can see portfolio activity. The Credit Controller records collection calls and promises-to-pay, which is the evidentiary backbone of the collections process ("third broken promise — recommending hold"). And complaints get typed as such, feeding a complaints view so recurring problems (wrong parts supplied, late deliveries) surface as patterns, not anecdotes.

Follow-ups turn the log from a diary into a workflow: any entry can set `follow_up_required` with a date, which lands on the owning user's follow-up queue and escalates to their manager when overdue.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Counter Sales | Log entries on any customer; view all non-restricted entries |
| Sales Rep | Full log/edit-own on portfolio customers; follow-up queue |
| Credit Controller | Full; entries of type `collection` (promise-to-pay fields) restricted to credit roles |
| Branch Manager | View all incl. restricted; reassign follow-ups; complaints dashboard |
| Workshop Advisor | Log entries linked to a vehicle/job |
| System Admin | Delete (soft) erroneous entries with reason |

## Workflow

Main process: log an interaction with follow-up.

```
Interaction happens (call / email / visit / complaint)
        │
Open customer profile → Communications tab → "Log Communication"
        │
Pick type ──> complaint? adds severity + category fields
        │
Subject + notes + outcome captured
        │
Follow-up needed? ──yes──> date + assignee set
        │no                     │
Entry saved on timeline         ▼
        │              Appears in assignee's follow-up queue
        │                       │
        │              Due date passes uncompleted
        │                       │
        │              Escalation: manager notified,
        │              entry flagged overdue
        ▼
Timeline updated; entry immutable after 24h (append corrections)
```

1. **Capture.** Staff log the entry from the profile (or directly from POS/workshop screens, which pre-link customer and vehicle). Speed matters: type, subject, notes, outcome — four fields for the common case.
2. **Classify.** Type drives downstream behaviour: `complaint` requires severity and category; collection entries capture promised amount and date.
3. **Follow-up.** Optional date + assignee (defaults to the author). Follow-ups form each user's daily queue, sorted by due date.
4. **Complete or escalate.** Completing a follow-up prompts logging the outcome as a new linked entry. Overdue follow-ups escalate to the assignee's manager after a configurable grace (default 2 business days).

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Customer profile — Communications tab | `customers.show` | Timeline of all interactions for one customer |
| Follow-up queue | dashboard widget + list | Each user's due and overdue follow-ups |
| Complaints view | via `customers.index` filters | All `complaint` entries across customers, by category/severity |

**Primary screen — Communications tab on customer profile:**
- **Header:** entry count, open follow-ups badge, open complaints badge, "Log Communication" button.
- **Main area:** reverse-chronological timeline; each entry shows type icon, subject, author, timestamp, outcome, follow-up status chip (due / overdue / done); filters by type, author, date range; restricted collection entries collapsed for non-credit roles.
- **Actions:** Log Communication, Complete Follow-up, Reassign Follow-up (Manager), Link to Vehicle/Job, Export Timeline.

## Fields & Validation

Log entry form:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| Type | select | Yes | `call`, `email`, `visit`, `note`, `complaint` (plus `collection` for credit roles) |
| Subject | text(255) | Yes | Min 5 chars |
| Notes | textarea | Yes | Min 10 chars; max 5000 |
| Outcome | text(255) | No | Encouraged; required for `collection` type |
| Follow-up required | boolean | No | — |
| Follow-up date | date | If follow-up | Today or future; ≤ 90 days out |
| Follow-up assignee | FK select | If follow-up | Active user; defaults to author |
| Complaint severity | select | Complaint | `low`, `medium`, `high`; `high` notifies Branch Manager immediately |
| Complaint category | select | Complaint | `wrong_part`, `late_delivery`, `pricing`, `staff`, `quality`, `other` |
| Promised amount / date | decimal + date | Collection | Amount > 0; date within 60 days |
| Linked vehicle / document | FK search | No | Customer's vehicle (5.4) or a sales/workshop document |

## Business Rules

1. Entries become immutable 24 hours after creation; corrections are logged as new entries linked to the original ("correction to entry #123"). Soft delete (Admin, with reason) hides but never destroys.
2. Every entry stamps `user_id` and `created_at` automatically — authorship is never editable.
3. `complaint` entries cannot be closed without an outcome; high-severity complaints require Branch Manager acknowledgement within 1 business day (tracked).
4. Collection-type entries and their promise-to-pay data are visible only to credit/finance roles and managers — a sales rep should not see "promised $8,000 by Friday" and pre-spend the customer's goodwill.
5. Promises-to-pay feed Credit Management (5.3): a broken promise (date passed, no receipt covering the amount) is auto-flagged on the credit dashboard.
6. Statement delivery failures (5.5) and credit-check overrides (5.3) write system-generated entries to the timeline, marked `system` authorship, so the timeline is genuinely complete.
7. Follow-ups belonging to a deactivated user are force-reassigned during user offboarding; none may be orphaned.
8. Timeline export (for a dispute or legal matter) renders the full unfiltered log as PDF, Manager permission required.

## Edge Cases & Error Handling

- **Customer phones a second branch about the same complaint:** logging a new complaint on a customer with an open complaint of the same category prompts "possible duplicate — link to existing?" so one issue does not become three statistics.
- **Follow-up due while assignee is on leave:** the queue supports manager bulk-reassignment; overdue escalation still fires so nothing waits silently for a return date.
- **Promise-to-pay partially kept:** the nightly check compares receipts since the promise date to the promised amount; partial payment marks the promise `partially_kept` rather than binary broken/kept, and the credit dashboard shows the shortfall.
- **Entry logged against the wrong customer:** within 24h the author can move it (audited); after immutability, Admin soft-deletes and the author re-logs on the right profile — the deletion reason references the new entry.
- **High-severity complaint at 17:55 Friday:** manager notification goes out immediately (email/in-app); the 1-business-day acknowledgement clock starts Monday.
- **Anonymous cash customer complains:** entries need a customer; the shared `cash` account accepts complaint entries with the complainant's name/phone in the notes so patterns (e.g. wrong-part complaints at one branch) are still countable.
- **Bulk email campaign to 500 customers:** marketing sends do not auto-spam the timeline; only campaigns flagged "log per customer" write entries, and those are batched as `email` type with the campaign reference.
