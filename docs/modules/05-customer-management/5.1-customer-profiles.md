# 5.1 Customer Profiles

> Master data for every customer — individual, business, fleet, dealer, and cash. Part of [Module 5: Customer Management](../05-customer-management.md).

## Purpose

The customer profile is the anchor record for everything the business knows about a buyer: identity, tax registration, addresses, contacts, pricing rules, credit standing, and assigned salesperson. Every sales document, workshop job, receipt, statement, and loyalty transaction hangs off a customer record (except anonymous `cash` sales, which post to a shared walk-in account).

For a motor spares business the distinction between customer types drives behaviour throughout the system. A retail car owner buys at retail price and earns loyalty points; a garage on a trade account buys at trade price on Net 30 terms and is subject to credit checks; a fleet operator may have a negotiated price list and consolidated monthly invoicing; a dealer (another spares shop) buys at near-wholesale margins. Getting the type and group right at creation time means the correct price list, discount, payment terms, and VAT treatment apply automatically at the point of sale — counter staff should never have to remember which garage gets which discount.

Profiles also carry compliance data: VAT registration numbers must be captured for trade customers who need tax invoices with their VAT number printed, and blacklist status must block sales to customers with a history of fraud or bad debt.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Counter Sales | Search and view profiles; create `individual` customers only; cannot edit credit fields |
| Sales Rep | Create and edit customers in own portfolio; request (not approve) credit limits |
| Branch Manager | Full create/edit at own branch; approve blacklist removal requests |
| Credit Controller | Edit credit limit, payment terms, on-hold, blacklist across all branches |
| Accounts Clerk | View all; edit contact/address and statement-delivery settings |
| System Admin | Full access including merge and delete (soft) |

## Workflow

Main process: onboarding a new customer.

```
Search existing → Not found → Select type → Capture details
      │                            │
   Found ──> Open profile          ├─ individual: name, phone, email
                                   └─ business/fleet/dealer: legal name,
                                      tax no, VAT no, contacts, addresses
                                          │
                              Assign group + price list + salesperson
                                          │
                    Trade account requested? ──yes──> Credit application
                                          │              (see 5.2 / 5.3)
                                          no
                                          │
                                   Save → CUST-XXXX issued → Active
```

1. **Duplicate search first.** Staff must search by name, phone, VAT number, or customer number before creating. The create screen surfaces near-matches (same phone or VAT number) as a blocking warning.
2. **Select customer type.** Type determines which fields become mandatory (e.g. VAT number for `business` requesting tax invoices).
3. **Capture identity, addresses, contacts.** At least one contact and one billing address are required for non-individual types.
4. **Assign commercial settings.** Customer group defaults the price list, discount, and payment terms; these can be overridden per customer with permission.
5. **Save.** The system issues the next `customer_number` (CUST-0001 sequence) and sets status `active`. Credit limit starts at 0 (cash only) until a credit application is approved.

## Fields & Validation

Main creation/edit form:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| Type | select | Yes | One of `individual`, `business`, `fleet`, `dealer` (`cash` is system-owned, not selectable) |
| Name | text(255) | Yes | Min 2 chars; blocked if exact duplicate of active customer with same phone |
| Trading name | text(255) | No | Business/fleet/dealer only |
| Tax number | text(30) | Business+ | Required for `business`, `fleet`, `dealer` |
| VAT number | text(30) | Conditional | Required if customer requests VAT tax invoices; format check per tax authority (e.g. 9–10 digits) |
| Customer group | FK select | Yes | Must be an active group; drives defaults |
| Price list | FK select | Yes | Defaults from group; override requires Manager |
| Payment terms | FK select | Yes | Defaults COD for new customers until credit approved |
| Salesperson | FK select | No | Active users with sales role only |
| Branch | FK select | Yes | Defaults to creating user's branch |
| Billing address | address block | Business+ | line1, city required; postal code 4–10 chars |
| Primary contact | contact block | Business+ | Name + at least one of email/phone; email RFC-valid; phone 7–20 digits |
| Email (individual) | email | No | Required only if statements/loyalty emails opted in |
| Notes | textarea | No | Max 2000 chars |

Credit limit, on-hold, and blacklist fields are **not** on the standard form — they are edited only via Credit Management (5.3) with its own permission checks.

## Business Rules

1. `customer_number` is immutable once issued; deleted (deactivated) numbers are never reused.
2. A customer with `status = blacklisted` cannot be selected on any new sales document, quote, or workshop job — including cash sales, if identified.
3. Only one `is_default` address per address type; setting a new default clears the previous one atomically.
4. Only one `is_primary` contact per customer; the primary contact defaults `receives_statements` and `receives_invoices` to true.
5. Changing customer group does **not** retroactively change price list / terms already overridden on the customer — the system prompts whether to re-apply group defaults.
6. A customer with a non-zero AR `balance`, open sales documents, or workshop jobs cannot be deactivated; the profile must be settled first.
7. VAT number is mandatory before the first credit sale to a `business` customer if their group is flagged as VAT-invoiced.
8. Merging duplicates (Admin only) re-parents all sales, receipts, vehicles, communications, and loyalty transactions to the surviving record and deactivates the duplicate, keeping an audit note on both.
9. Individual customers created at POS mid-sale get a minimal profile (name + phone) that is flagged `incomplete` for back-office enrichment.

## Edge Cases & Error Handling

- **Duplicate VAT number entered:** save is blocked with a link to the existing customer; Credit Controller can override for legitimate cases (e.g. two branches of one franchise trading separately).
- **Walk-in refuses to give details:** sale proceeds against the shared `cash` customer; no loyalty points accrue and no returns-by-account lookup is possible — receipt number becomes the only proof.
- **Customer group deleted while in use:** groups with members cannot be deleted; the UI offers "deactivate group" instead, which keeps existing members but blocks new assignment.
- **Salesperson leaves the company:** deactivating a user prompts reassignment of their customer portfolio; profiles are never left pointing at an inactive user silently.
- **Two clerks create the same garage simultaneously:** unique-phone/VAT soft check races are caught by a database unique constraint on `(vat_number)` where non-null; the second save fails with a merge suggestion.
- **Address used on open delivery:** editing a delivery address warns if open sales orders reference it; historical documents keep a snapshot of the address at time of sale.
- **Blacklisted customer walks in with cash:** POS shows the blacklist banner and reason; Branch Manager PIN required to proceed even for cash.
