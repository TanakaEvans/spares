# 6.1 Supplier Profiles

> Master record for every supplier the business buys from. Part of [Module 6: Supplier Management](../06-supplier-management.md).

## Purpose

The supplier profile is the counterpart of the customer profile on the buying side: it holds identity, tax and VAT registration, the currency the supplier trades in, our credit terms with them, banking details for payment, and the operational facts that drive purchasing — average lead time and minimum order value. Every purchase order, goods received note (GRN), supplier invoice, and payment references a supplier record.

A spares business buys from a mix that the `type` field captures: local distributors delivering daily (brake pads, filters), importers with 6–12 week lead times and foreign-currency price lists (engine components ex-Japan or Germany), manufacturers/OEMs supplying direct, and wholesaler buying groups. Type matters operationally — an `import` supplier's profile carries a foreign `currency_id`, and its lead time feeds reorder-point calculations in Inventory very differently from a same-day local distributor.

Banking details deserve special care: they are the payment destination for AP payment runs ([7.4](../07-finance-accounts/7.4-accounts-payable.md)), and supplier-banking-detail fraud (a spoofed "we've changed banks" email) is one of the most common ways businesses lose money. The profile therefore treats bank fields as high-sensitivity data with dual control on changes.

| Role | Access |

| Purchasing Manager | Approve new suppliers; edit all except bank details |

## Workflow

Main process: onboarding a new supplier.

```
Buyer identifies need for new supplier
        │
Duplicate search (name, VAT number, supplier number)
        │
Capture profile: identity, type, currency, tax/VAT numbers,
addresses, contacts, lead time, MOQ
        │
Capture bank details ──> verification call to a known number
        │                 (not the number on the email!)
        │
Purchasing Manager approval ──> supplier `pending` → `active`
        │
Financial Manager confirms bank details (dual control)
        │
SUPP-XXXX active ──> available on POs; payable via payment run
```

1. **Search first.** Duplicate suppliers fragment spend history and break performance KPIs (6.4); the create screen surfaces VAT-number and name matches.
2. **Capture master data.** Type, currency, and payment terms are mandatory; lead time and minimum order value default from type but should reflect reality — Inventory's reorder engine consumes them.
3. **Verify banking.** Bank details are entered but held `unverified` until a second person confirms them via an independent channel; unverified suppliers cannot be included in a payment run.
4. **Approve.** Purchasing Manager activates the supplier; the approval, like every subsequent edit, is audit-logged.

**Primary screen — Supplier detail (`suppliers.show`):**
- **Header:** supplier number, name/trading name, type badge, active/inactive status, current AP balance, our credit limit with them, bank-verification status chip.
- **Main area:** tabbed panels — Details (identity, tax, currency, terms, banking [masked], addresses), Purchase Orders, Invoices & Payments, Price Lists (6.2), Approved Parts (6.3), Performance (6.4), Contacts (6.5).
- **Actions:** New Purchase Order, Record Invoice, Edit, Change Bank Details (dual-control flow), Deactivate.

## Fields & Validation

Supplier create/edit form:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| Name | text(255) | Yes | Min 2 chars; near-duplicate warning on save |
| Trading name | text(255) | No | |
| Type | select | Yes | `local`, `import`, `manufacturer`, `distributor`, `wholesaler` |
| Tax number | text(30) | Yes | Company registration format check |
| VAT number | text(30) | Conditional | Required for VAT-registered local suppliers (input VAT claims depend on it); unique among active suppliers |
| Currency | FK select | Yes | Local currency for `local`; any active currency for `import` |
| Payment terms | FK select | Yes | Active `payment_terms` record |
| Credit limit | decimal(15,2) | No | ≥ 0; our facility with them — informational cap for PO exposure |
| Lead time (days) | int | Yes | 0–365; sanity warning if `local` > 14 or `import` < 7 |
| Minimum order value | decimal(15,2) | No | ≥ 0; enforced as a warning at PO submission |
| Bank name / branch code / account no / account name | text | For payment | Branch code numeric 6 digits; account number 6–30 digits; account name should match supplier legal name (mismatch warning) |
| Physical address | address block | Yes | line1, city, country required |
| Primary contact | contact block | Yes | Name + email or phone (see 6.5) |

## Business Rules

1. `supplier_number` (SUPP-0001) is immutable and never reused.
2. Bank-detail changes require **dual control**: the editor submits, a Financial Manager approves; until approved, payments continue to the previous verified details. Every change stores old and new values, both users, and the verification method.
3. Suppliers with unverified bank details are excluded from payment runs ([7.4](../07-finance-accounts/7.4-accounts-payable.md)) — the run screen lists them as blocked with reason.
4. A supplier cannot be deactivated with open purchase orders, unmatched GRNs, or a non-zero AP balance; the profile lists exactly what is blocking.
5. Changing a supplier's currency is blocked once any transaction exists; a genuine currency switch means a new supplier record (cross-referenced in notes) so historic costs stay coherent.
6. VAT number is required before input VAT can be claimed on the supplier's invoices; invoices from suppliers without a VAT number post gross with no input VAT line ([7.6](../07-finance-accounts/7.6-vat-management.md)).
7. Lead time on the profile is the default; part-specific lead times on the approved supplier list (6.3) override it.
8. Merging duplicate suppliers (Admin) re-parents POs, GRNs, invoices, payments, price lists, and approved-supplier rows to the survivor, then deactivates the duplicate with a cross-reference.

## Edge Cases & Error Handling

- **"We've changed our bank account" email arrives:** the AP clerk enters the change, which parks as pending; policy requires call-back verification to the phone number on file (not the email), and the Financial Manager approval screen shows the verification note before allowing approval.
- **Import supplier quotes in EUR but invoices in USD:** currency is per-supplier; a second trading currency means a second supplier record or a formal currency change decision — the invoice-capture screen blocks currency mismatches with the profile.
- **Duplicate created anyway (typo in name, blank VAT):** performance and spend reports allow ad-hoc grouping while the merge is pending; merge is the durable fix.
- **Supplier acquired / renamed:** rename in place (history preserved, number unchanged) with the former name kept in `trading_name` or notes; a new legal entity with a new tax number is a **new supplier**, old one deactivated after wind-down.
- **MOQ raised by supplier mid-quarter:** updating `minimum_order_value` affects new POs only; open POs below the new MOQ are flagged for buyer attention, not auto-changed.
- **Two buyers edit the same profile concurrently:** last-write-wins is prevented by optimistic locking; the second save shows a diff of the conflicting fields.
- **Supplier is also a customer (a garage that both buys and supplies second-hand cores):** the records are deliberately separate (customer in Module 5, supplier here); contra settlements are handled in Finance, never by netting master records.
