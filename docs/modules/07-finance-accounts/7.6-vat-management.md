# 7.6 VAT Management

> Output and input VAT tracking and the periodic VAT return to the tax authority. Part of [Module 7: Finance & Accounts](../07-finance-accounts.md).

## Purpose

The business collects VAT on behalf of the tax authority: 15% standard rate on virtually every part and labour hour sold (output VAT, posted CR 2210 at invoicing), while reclaiming the 15% paid on stock purchases and expenses (input VAT, DR 2220 at supplier-invoice capture). Periodically — typically every two months for a VAT-registered spares business — the difference is declared and paid over on a VAT return. Getting this wrong is not a reporting blemish; it is penalties, interest, and audits.

The design principle from the parent module is that VAT is **calculated at posting time on every transaction, never cached**: the VAT amount on each journal is derived from the transaction's lines and rate codes at the moment it posts, so the return is an extraction over posted journals in the period, reconcilable line-by-line back to source documents. A VAT-registered garage customer's tax invoice shows their VAT number and the VAT split; a zero-rated export sale carries its rate code and the exemption evidence; and the return's boxes are sums the auditor can drill.

The rate table is small — `STD` 15%, `ZERO` 0%, `EXEMPT` — but the edge semantics matter: zero-rated sales still appear on the return (at 0), exempt supplies do not enter the VAT computation at all, and input VAT is only claimable on invoices from VAT-registered suppliers with valid tax invoices.

## Workflow

Main process: preparing and submitting a VAT return.

```
VAT period ends (e.g. Jan–Feb)
        │
Create draft return for period_start → period_end
        │
System extracts from posted journals:
  output VAT: all CR/DR 2210 movements  ── drill: sales docs
  input VAT:  all DR/CR 2220 movements  ── drill: supplier invoices
        │
Reconciliation checks:
  ├─ output VAT ≈ 15% of standard-rated sales? (variance report)
  ├─ input claims all have supplier VAT numbers?
  └─ zero-rated sales all have exemption evidence?
        │
Exceptions resolved (correcting journals via 7.2)
        │
net_vat = output − input
        │
FM review ──> status `submitted` (filed with authority)
        │
Payment made via AP/bank ──> status `paid`, journal:
DR VAT Control 2230, CR Bank
        │
Period's VAT-relevant journals flagged "included in return"
```

1. **Extract.** The draft return sums the VAT accounts' movements for the period, with every figure drillable to journal lines and onward to source documents.
2. **Reconcile.** Built-in checks compare VAT to the implied base amounts and hunt for structural errors: claims without VAT numbers, manual journals touching VAT accounts, out-of-period stragglers.
3. **Correct.** Errors found are fixed by correcting journals with full audit trail (parent rule) — the extraction is then re-run; the return itself is never hand-edited.
4. **Submit and pay.** Submission freezes the return's figures; the payment (or refund, when input exceeds output) is processed through the normal bank/AP flow and linked back.

## Fields & Validation

Return preparation and rate configuration:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| Period start / end | date | Yes | Contiguous with the previous return (no gaps/overlaps); end < today |
| Output VAT / input VAT | decimal(15,2) | System | Extracted, not typed; manual override impossible |
| Net VAT | decimal(15,2) | System | output − input; negative = refund due |
| Status | select | Yes | `draft` → `submitted` → `paid`; transitions one-way, FM permission for submit |
| Submission reference | text(100) | On submit | Tax-authority filing reference |
| Rate table: code / rate | text + decimal | Admin | `STD` 15.00, `ZERO` 0.00, `EXEMPT` n/a; rate changes take an effective date and never mutate history |
| Customer zero-rating | flag + document | Per customer | Valid exemption certificate on file with expiry date; expired certificate reverts the customer to STD |

## Business Rules

1. VAT is calculated on every transaction at posting — never stored as a cached period total (parent rule); the return is always reproducible from journals.
2. Adjustments to VAT returns require a correcting journal with full audit trail (parent rule); corrections discovered **after submission** go into the next period's return as declared adjustments, matching how tax authorities expect them.
3. Zero-rated customers must hold a valid exemption certificate on file (parent rule); the sales flow blocks zero-rating without one, and certificate expiry reverts pricing to standard-rated automatically with a warning to the salesperson.
4. Input VAT is claimable only from suppliers with a captured VAT number ([6.1](../06-supplier-management/6.1-supplier-profiles.md)) and a valid tax invoice; supplier invoices without these post gross, and the exception report lists forgone claims so the AP clerk can chase proper invoices.
5. Manual journals may not post directly to VAT Output (2210) or Input (2220) except via the correcting-journal flow with reason codes — the accounts are otherwise fed only by document postings.
6. Rate changes (legislation) are configured with an effective date; documents compute VAT by their **tax point date** (invoice date), so a sale invoiced before the change at 15% remains 15% even if captured after.
7. A submitted return's figures are frozen; re-extraction is disabled and the underlying period should already be closed ([7.8](7.8-period-management.md)) — submitting a return over an open period raises a warning.
8. Credit notes carry negative output VAT into the period they are issued, not the period of the original invoice.
9. The VAT control (2230) reflects output minus input; the return detail reconciles its computed net to the control balance and blocks submission on unexplained differences.

## Edge Cases & Error Handling

- **Export sale zero-rated but proof of export never arrives:** the exception check lists zero-rated sales missing evidence past the grace period; the fix is a correcting adjustment converting the sale to standard-rated — the VAT comes out of the business's margin, which is exactly why the counter demands paperwork.
- **Supplier invoice dated last period arrives after that return was submitted:** input VAT is claimed in the current period (rule 2's next-period mechanism) — legitimate and standard; the workings show it as a prior-period input claim.
- **Customer's exemption certificate expired mid-period:** sales before expiry stay zero-rated, after expiry are standard-rated; the certificate-expiry report warned 30 days ahead.
- **Cash rounding at POS creates 1-cent VAT discrepancies:** per-document VAT rounds half-up per line then sums; the return-vs-base variance report tolerates the accumulated rounding within a documented threshold, itemising anything beyond it.
- **Return computes to a refund (big import stock-up month):** negative net VAT flows the refund path — status `submitted`, and the eventual receipt from the authority matches on the bank rec ([7.5](7.5-cash-bank-management.md)) against the return reference.
- **Someone back-dates a sale into a period whose return is already submitted:** period close should prevent this ([7.8](7.8-period-management.md)); if the period was still open, the VAT-relevant journal is flagged "posted after return submission" and swept into the next return's adjustment box automatically.
- **Two rates in one document (standard parts + zero-rated export freight):** line-level rate codes are supported; the document VAT is the sum of line VAT, and the return buckets each line by its code.
