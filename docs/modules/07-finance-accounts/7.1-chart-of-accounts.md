# 7.1 Chart of Accounts

> The account structure every journal in the system posts to. Part of [Module 7: Finance & Accounts](../07-finance-accounts.md).

## Purpose

The chart of accounts (COA) is the skeleton of the entire finance module: a coded, typed hierarchy of GL accounts — assets, liabilities, equity, revenue, expenses — that every automatic and manual journal posts against. When a counter sale posts DR Bank / CR Sales Revenue / CR VAT Output, those three legs land on specific COA accounts; get the COA wrong and every report downstream (trial balance, P&L, balance sheet, VAT return) is wrong with it.

For a spares business the COA reflects the trade: revenue split between retail parts, trade parts, workshop labour, and oils/lubricants (so gross margin by stream is reportable); COGS accounts including stock write-offs and supplier rebates; inventory asset accounts including parts in transit; and the liability side carrying VAT Output/Input/Control and lay-by deposits as deferred revenue. The reference structure in the [parent module](../07-finance-accounts.md#71-chart-of-accounts) ships as the seed COA and is tailored per installation.

Two properties keep the ledger honest. **Control accounts** (Trade Debtors, Trade Creditors, Inventory) mirror sub-ledgers and accept postings only from those sub-ledgers — never manual journals — so AR/AP/stock always reconcile to the GL. And **normal balance** typing per account lets the system sanity-check postings and present balances with correct sign conventions on reports.

## Workflow

Main process: adding a new account and wiring it into posting.

```
Need identified (e.g. new revenue stream: "Sales - Batteries")
        │
Accountant proposes: code (within 4xxx range), name, type,
category, normal balance
        │
Financial Manager reviews:
  code fits hierarchy? type consistent with range?
  really new, or belongs under an existing account?
        │approve
Account created (is_active = true, allow_direct_posting per type)
        │
Posting mappings updated (e.g. product category "Batteries"
→ revenue account 4500) so automatic journals hit it
        │
First postings arrive ──> account appears on TB / P&L
```

1. **Propose.** New accounts are the exception, not the routine — most needs are met by existing accounts plus reporting dimensions (branch, category).
2. **Validate structure.** Code must sit in the range matching its type (1xxx assets … 6xxx+ expenses per the seed structure); type and `normal_balance` must agree (`asset`/`expense` → debit; `liability`/`equity`/`revenue` → credit).
3. **Create.** Control-account and direct-posting flags set correctly at birth — `is_control_account = true` forces `allow_direct_posting = false`.
4. **Map.** Automatic posting configuration (which account each transaction type hits) is updated; unmapped transaction types cannot post and fail loudly, never default silently.

## Fields & Validation

Account create/edit form:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| Account code | text(20) | Yes | Unique; numeric; must fall in the range for its type (1xxx–1999 asset, 2xxx liability, 3xxx equity, 4xxx revenue, 5xxx COGS, 6xxx+ expense); immutable after first posting |
| Name | text(255) | Yes | Unique within type |
| Type | select | Yes | `asset`, `liability`, `equity`, `revenue`, `expense`; immutable after first posting |
| Category | select | Yes | Consistent with type (e.g. `current_asset` only under `asset`); drives report grouping |
| Normal balance | select | Yes | Auto-derived from type; override blocked |
| Is control account | boolean | Yes | If true: `control_type` required, `allow_direct_posting` forced false |
| Control type | select | Control only | `debtors`, `creditors`, `inventory`; at most one **active** control account per control type |
| Allow direct posting | boolean | Yes | False for control accounts and header/summary accounts |
| Is active | boolean | Yes | Deactivation rules below |
| Notes | textarea | No | Intended use, mapping references |

## Business Rules

1. Control accounts cannot receive manual journal lines (parent rule [7.2](7.2-general-ledger.md#business-rules)); the account picker on manual journals excludes them entirely rather than failing at post time.
2. Exactly one active control account per `control_type` — a second active `debtors` control is blocked, because sub-ledger reconciliation depends on a single mirror account.
3. Account code and type are immutable once the account has postings; corrections mean a new account plus a transfer journal, preserving history.
4. An account cannot be deactivated while it has a non-zero balance or is referenced by any active posting mapping; the deactivation screen lists the blockers.
5. Deleting accounts is not supported at all — deactivate only; historical journals must always resolve to a real account.
6. Every automatic posting type (see the [posting architecture table](../07-finance-accounts.md#posting-architecture)) must map to an active, postable account; saving a mapping to an inactive or non-postable account is blocked, and transactions with a missing mapping fail with an explicit "unmapped posting: COGS for category X" error.
7. VAT accounts (Output 2210, Input 2220, Control 2230) are flagged system-reserved: rename allowed, deactivate/remap requires acknowledging the impact on VAT return extraction ([7.6](7.6-vat-management.md)).
8. COA changes (create, edit, deactivate, mapping change) are audit-logged with user, timestamp, and before/after values.

## Edge Cases & Error Handling

- **New product category sells before its revenue mapping exists:** the sale's posting fails fast at invoice time with the unmapped-posting error naming the category; the fallback is an explicit "Uncategorised Sales" mapping the Financial Manager may enable — never a silent default.
- **Bookkeeper tries to journal directly to Trade Debtors Control to "fix" a customer balance:** impossible via UI (picker excludes control accounts); the correct path is an AR document ([7.3](7.3-accounts-receivable.md)) so the sub-ledger and GL move together.
- **Two installations merged / COA restructure wanted:** restructuring is a year-end project: new accounts created, mappings switched at a cutover date, old accounts left active until balances transfer by journal, then deactivated — the COA screen's "restructure checklist" export supports this.
- **Account deactivated while a recurring journal template references it:** deactivation blocker list includes journal templates; the template must be edited first.
- **Balance on a deactivated account from a back-dated posting:** back-dated journals validate account active-status **as at the journal date**, so posting into a period when the account was active is allowed; the account then shows a residual balance and is flagged for transfer.
- **Seed COA loaded twice at installation:** the importer is idempotent on account code — re-runs update names/flags, never duplicate codes.
- **P&L category shows odd grouping after an edit:** category-type consistency validation prevents e.g. a `revenue` account categorised `current_asset`; report grouping issues therefore trace to mapping, not COA typing.
