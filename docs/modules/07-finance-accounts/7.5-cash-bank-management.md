# 7.5 Cash & Bank Management

> Bank accounts, cash books, and statement reconciliation — proving the GL against the bank. Part of [Module 7: Finance & Accounts](../07-finance-accounts.md).

## Purpose

Everything in the ledger ultimately claims that money moved; bank reconciliation is where those claims are proven. This sub-module maintains the register of bank accounts (each linked one-to-one with a GL account like 1120 Bank Account - Main), imports bank statements (CSV/OFX), and matches statement lines to GL entries — receipts from AR ([7.3](7.3-accounts-receivable.md)), payment batches from AP ([7.4](7.4-accounts-payable.md)), bank charges, and direct debits. A reconciled account means every statement line is explained and every GL bank entry has either cleared or is a known outstanding item.

For a spares business with tills, cash is the other half. Till floats and daily cash-ups happen in the Sales/POS module, but the banking of cash lands here: a deposit of Tuesday's takings must appear on the statement and match the till-to-bank transfer journal. Differences — a deposit short by $100 — surface in reconciliation, which is precisely the point: reconciliation is the daily fraud and error detector, not a month-end chore.

Reconciliation quality gates the rest of Finance: period close ([7.8](7.8-period-management.md)) requires reconciliations current for all active accounts, and the cash-flow visibility (current balances, uncleared payments) feeds the payment-run decision of what the business can afford to pay this week.

## Workflow

Main process: bank reconciliation.

```
Download statement from bank (CSV/OFX)
        │
Import ──> parse, dedupe (already-imported lines skipped
by date+amount+reference hash), lines stored
        │
Auto-match pass:
  exact: amount + reference (EFT batch refs, receipt refs)
  fuzzy: amount + date ±2 days (flagged for confirm)
        │
Manual matching for the rest:
  ├─ statement line ↔ one GL entry
  ├─ one-to-many (single deposit = several receipts)
  └─ no GL entry exists? ──> create adjustment journal
       (bank charges, interest, direct debits)
        │
Mark matched lines cleared
        │
Reconciliation summary:
  statement closing balance
  = GL balance + uncleared payments − uncleared deposits
        │
Balances agree ──> complete + print reconciliation report
Balances differ ──> difference itemised; cannot complete
```

1. **Import.** Bank-specific parser profiles map each bank's CSV/OFX layout; import is idempotent so re-importing an overlapping date range never duplicates lines.
2. **Auto-match.** References written at source (receipt bank refs from 7.3, EFT batch refs from 7.4) are what make auto-match rates high — the modules are designed to reconcile.
3. **Manual match.** The clerk resolves the remainder, including one-to-many groupings for consolidated deposits.
4. **Adjust.** Statement lines with no GL counterpart (charges, interest) generate pre-filled adjustment journals to the mapped accounts (e.g. 6500 Bank Charges), posted via GL rules ([7.2](7.2-general-ledger.md)).
5. **Complete.** The reconciliation locks its cleared marks and produces the report: cleared items, outstanding deposits, outstanding payments, and the balance proof.

## Fields & Validation

Bank account form and import:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| Name | text(100) | Yes | Unique; e.g. "Main Cheque Account" |
| Bank name / branch code | text | Yes | Branch code numeric 6 digits |
| Account number | text(30) | Yes | 6–30 digits; unique among active accounts |
| Currency | FK select | Yes | Immutable after first transaction |
| GL account | FK select | Yes | Active asset account, not a control account, one-to-one (an account already linked is rejected) |
| Opening balance | decimal(15,2) | Yes | Set once at creation; changes require FM approval and an opening-balance journal |
| EFT export format | select | For AP | Bank-specific format profile used by payment runs ([7.4](7.4-accounts-payable.md)) |
| Statement file | upload | Yes | .csv/.ofx ≤ 10 MB; parser profile must validate header layout; rejected files report the first bad row |
| Statement line match | action | — | Amounts must equal exactly across the match group (line vs GL entry or sum of entries); date differences allowed, amount differences never — differences are adjustments, not matches |

## Business Rules

1. Every bank account maps one-to-one to a GL account; the `current_balance` shown is always derived from the GL, never maintained independently (parent note: "From GL").
2. Statement import is idempotent (dedupe hash on date + amount + reference + running balance); a gap between the last imported line's balance and the new file's opening balance blocks import with a "missing statement period" error.
3. A statement line can only be reconciled once; unmatching is allowed until the reconciliation containing it is completed, after which changes require reopening (FM approval, audited).
4. Matches must balance to the cent (rule above); bank charges deducted from a deposit are two records — the gross deposit match and a charges adjustment — never a fudged match.
5. Adjustment journals created from reconciliation post through normal GL rules ([7.2](7.2-general-ledger.md)): open period, mapped accounts, audit trail.
6. Completing a reconciliation requires a zero difference; FM may complete with itemised outstanding queries only in exceptional cases, and those items carry forward flagged to the next reconciliation.
7. Uncleared GL payments older than a configurable age (e.g. 60 days — a cheque never cashed, an EFT that never left) escalate to the Accountant for reversal or investigation.
8. Period close ([7.8](7.8-period-management.md)) requires all active bank accounts reconciled to a statement date on or after period end.
9. Cash banked from tills must match the POS cash-up's declared banking amount; variances post to a cash over/short account and are reported per cashier.

## Edge Cases & Error Handling

- **Deposit on the statement $100 short of the till banking journal:** no match possible (amounts differ); the clerk records a $100 adjustment to cash over/short referencing the cash-up, and the variance report flags the till/cashier for follow-up.
- **One EFT batch of 38 supplier payments appears as one statement line:** the batch reference auto-matches the single statement line to the batch's GL total; drill-down shows the 38 payments ([7.4](7.4-accounts-payable.md)).
- **Customer pays directly into the bank with a useless reference ("SPARES"):** the unmatched line is assigned to the AR clerk, who identifies the payer, captures the receipt ([7.3](7.3-accounts-receivable.md)) with the statement reference, and the line then matches.
- **Bank changes its CSV layout:** the parser profile validation fails the import with the first unrecognised column; the profile is updated (Admin) — lines are never mis-parsed into wrong columns silently.
- **Same statement imported from two overlapping downloads:** dedupe skips existing lines and reports "412 lines: 380 new, 32 duplicates skipped".
- **Duplicated charge by the bank, refunded next month:** both lines are real — matched to a charge adjustment and a reversing adjustment respectively; reconciliation records reality, disputes happen with the bank.
- **Reconciliation reopened after period close to fix a mismatch:** reopening requires FM approval; resulting adjustment journals must post to the current open period, keeping the closed period intact ([7.8](7.8-period-management.md)).
- **Foreign-currency account:** statement and GL both in account currency; revaluation to local currency at period end is a Finance journal, outside reconciliation — the rec always balances in native currency.
