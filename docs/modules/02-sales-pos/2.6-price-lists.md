# 2.6 Price Lists

> Tiered pricing — retail, trade, wholesale, VIP — with a deterministic resolution order and full audit. Part of [Module 2: Sales & POS](../02-sales-pos.md).

## Purpose

A spares business sells the same Bosch alternator to a walk-in retail customer at full price, to the garage down the road at trade minus 15%, and to a reseller at wholesale minus 30%. Price lists make those tiers systematic: each customer is assigned a list, and every quote, order, POS sale, and invoice resolves its prices from that assignment automatically. The alternative — cashiers hand-discounting from memory — leaks margin, invites favouritism, and makes month-end analysis meaningless.

The design supports both shapes of tiered pricing: fixed prices per part (a negotiated $85.00 on `ELE-ALT-0310` for a key account) and percentage discounts off retail (trade list = retail − 15%), with quantity breaks via `minimum_qty` (buy 12+ oil filters, get the better rate). A strict resolution order — customer override, then part-on-list, then category discount, then list global discount, then default retail — makes every price explainable: the screen can always answer "why is it this price?".

Governance completes the picture: lists carry effective and expiry dates for planned price changes, staff below an authority threshold cannot sell below list minimums, and every price change is audited with before/after values so margin erosion is traceable to a person and a date.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Cashier / Counter Sales | See resolved prices; view "why this price" breakdown |
| Sales Supervisor | Override within tolerance; assign customers to standard lists |
| Pricing Clerk | Maintain list items, run bulk updates (draft) |
| Sales / Branch Manager | Create lists, approve bulk changes, set customer overrides, assign VIP/custom lists |
| Finance | Margin reports, audit review |

## Workflow

```
Create price list (type, currency, tax-inclusive?, effective date)
        │
        ▼
Populate: fixed prices per part  and/or  discount % (global, category, part)
        │
        ▼
Assign customers to the list (default: retail)
        │
        ▼
[Every transaction line] resolution order:
   1. customer-specific override price
   2. part-specific price on customer's list
   3. category discount on customer's list
   4. list global discount %
   5. default (retail) list price
        │
        ▼
Maintenance: bulk update (cost-plus / % uplift) → review draft → approve → effective
        │
        └── list expires ──► customers auto-fall-back to default list
```

1. Manager creates the list; the tax-inclusive flag decides whether stored prices contain VAT (retail counter lists usually inclusive, trade lists exclusive).
2. The pricing clerk populates items — imports from supplier cost files with markup rules, or manual entry for negotiated lines.
3. Customer assignment happens on the customer record; a customer always has exactly one active list.
4. At transaction time, resolution walks the order above and stops at the first hit; the resolved source is stored on the line for the "why this price" display.
5. Bulk updates (e.g. "uplift all Filters 8% from 1 March") are staged as drafts with a margin-impact preview, approved, and applied on the effective date.

## Fields & Validation

Price list header:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| name | string(100) | Yes | Unique |
| type | enum | Yes | `retail`, `trade`, `wholesale`, `vip`, `custom` |
| currency_id | FK | Yes | Active currency |
| is_tax_inclusive | boolean | Yes | Locked once transactions reference the list |
| effective_date | date | Yes | — |
| expiry_date | date | No | > effective_date; null = open-ended |
| is_default | boolean | Yes | Exactly one default list system-wide (enforced) |

Price list item:

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| part_id | FK | Yes | Active part; unique per list (+ min qty band) |
| price | decimal(15,2) | Cond. | Either price OR discount_pct, not both; > 0 |
| discount_pct | decimal(5,2) | Cond. | 0–100 |
| minimum_qty | decimal(10,2) | No | ≥ 1; bands must not overlap for the same part |
| — | — | — | Warning (not block) when resulting price < average cost |

## Business Rules

1. Every customer has exactly one active price list; unassigned or expired assignments fall back to the default (`retail`) list automatically.
2. Resolution is strict and first-match ([order above](#workflow)); the winning source is stored per transaction line for auditability.
3. Expired lists stop resolving on expiry+1; customers on them fall back to default and the assignment is flagged for review — prices never silently freeze.
4. Staff below the pricing-authority threshold cannot set a line price below the resolved list price; supervisor override records approver, reason, and delta.
5. Selling below average cost triggers a hard warning and manager approval regardless of authority level.
6. All price and assignment changes are audited: user, timestamp, before/after values; bulk updates audit per item.
7. Quantity breaks apply per line quantity, not summed across lines or documents.
8. `is_tax_inclusive` cannot change once the list has been used — flipping it would silently reprice history displays; create a successor list instead.
9. Future-dated approved changes apply automatically on their effective date; drafts never affect live pricing.
10. Custom (one-customer) lists must name their customer; assigning a second customer converts them to `vip` type with a warning.

## Edge Cases & Error Handling

- **Part on no list and no retail price**: transaction line blocks with "no price on file" and a task to the pricing clerk — the system never invents zero.
- **Overlapping quantity bands** (min 10 and min 12 both matching qty 15): validation prevents creating overlaps; existing bad data resolves to the highest qualifying band and is reported.
- **Currency mismatch** (trade list in USD, invoice in ZWG): resolution converts at the document's `exchange_rate` snapshot; the line notes the source currency.
- **Customer's negotiated override on a superseded part**: override does not auto-carry to the successor part; the assignment review report flags it for renegotiation.
- **Bulk import with a price of 0.00**: rejected to the exceptions report (0 is treated as missing, not free).
- **Trade customer buys below their qty break** (11 filters, break at 12): resolved at standard rate; POS hints "add 1 more for the 12+ price" — an upsell, not an error.
- **Two clerks edit the same item concurrently**: optimistic locking; the second save shows the fresh value and requires re-confirmation.
- **List expiry mid-document** (quote priced yesterday, converting today after expiry): conversion re-resolution ([2.2 rule 2](2.2-quotations.md)) surfaces the change; the expired list is simply no longer a source.
- **Inclusive list used with a VAT rate change**: inclusive prices keep their gross value; the excl/VAT split recomputes at the new rate, and the margin report flags the effective ex-VAT price drop for review.
