# 2.4 Tax Invoices

> The legal, gapless-numbered tax document; the trigger for revenue, VAT output, and AR. Part of [Module 2: Sales & POS](../02-sales-pos.md).

## Purpose

The tax invoice is the one document in the sales flow with legal weight. It is what the VAT authority audits, what the customer's bookkeeper files, and what drives the general ledger: posting an invoice recognises revenue, raises VAT output, and creates the receivable (or matches the cash taken at POS). Everything upstream — quotes, orders, picks — is operational; the invoice is fiscal.

Because of that, invoices behave differently from every other document. Numbers are strictly sequential and gapless (INV-YYYYMMDD-XXXX) so an auditor can verify none are missing; posted invoices are immutable, with corrections flowing only through credit notes; and the invoice date must fall in an open financial period. VAT handling covers exclusive and inclusive pricing modes and multiple rates on one document (standard-rated brake pads next to zero-rated exports), always computed from system prices rather than trusting a hand-typed total.

The sub-module also covers the practical variants: proforma invoices for customers who need paperwork before committing (no GL posting, no fiscal number), batch invoicing that rolls a month of fulfilled orders per fleet customer into single invoices, and controlled reprints watermarked "COPY" so duplicates cannot pass as originals.

## Workflow

```
Source: POS payment │ fulfilled sales order │ manual entry │ proforma acceptance
        │
        ▼
Draft invoice built (lines, prices, VAT per line)
        │
        ▼
Validation: open period? customer OK? prices/VAT recomputed?
        │
        ▼
POST  ──► fiscal number assigned (gapless, atomic)
        ├──► stock ledger: SALE entries per part line
        ├──► GL: Dr AR/Cash · Cr Sales · Cr VAT output
        └──► document locked (immutable)
        │
        ▼
Print / email PDF ──► payment allocation (POS: immediate; account: via AR)
        │
        └── error discovered later ──► Credit Note (2.5) — never an edit
```

1. Most invoices are born posted via POS (payment and posting are one transaction). Order-based invoices are drafted from delivered quantities and posted deliberately.
2. Posting assigns the next number from the branch's fiscal sequence inside the posting transaction — the number does not exist until posting succeeds.
3. GL postings are generated per line using category GL defaults ([1.8](../01-inventory-management/1.8-category-management.md)) and per-line VAT codes.
4. Account invoices join the AR ageing; `due_date` derives from the customer's credit terms, which print on the document.
5. Reprints render with a "COPY" watermark and a reprint counter; proformas carry a distinct PRO- number range and no fiscal effect.

## Fields & Validation

Main form: invoice (manual/draft path; POS builds this automatically).

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| customer_id | FK | Yes | Active; account invoices require credit terms on file |
| document_date | date | Yes | Within an open financial period; not future beyond tolerance (1 day) |
| due_date | date | Auto | document_date + customer terms; ≥ document_date |
| price_list_id | FK | Auto | From customer; locked at posting |
| lines[].part_id | FK | Cond. | Required for `part` lines |
| lines[].qty | decimal(10,2) | Yes | > 0; for order-sourced invoices ≤ undelivered-uninvoiced balance |
| lines[].unit_price | decimal(15,2) | Yes | System-resolved; overrides within authority, audited |
| lines[].vat_code | string(10) | Yes | Valid active code; rate snapshot stored on line |
| totals | decimal(15,2) | Auto | Always recomputed server-side from lines — client totals are never trusted |

## Business Rules

1. Posted invoices are immutable — no field edits, no line changes, no deletion. Corrections are credit notes ([2.5](2.5-credit-notes-returns.md)) plus, where needed, a new invoice.
2. Invoice numbers are sequential and gapless per branch sequence; number assignment happens inside the posting transaction, so a failed post consumes no number.
3. The invoice date must fall in an open financial period; period close blocks new postings dated into it.
4. VAT is always calculated per line on system prices (respecting the price list's inclusive/exclusive mode) and summed per rate; a manually typed grand total is never accepted as the basis.
5. Rounding: VAT rounds per line to 2dp; the per-rate subtotal is the sum of line VAT (no re-derivation from subtotals), preventing 1-cent audit mismatches.
6. Multiple VAT rates coexist on one invoice; each line stores `vat_rate` as at posting so later rate changes never rewrite history.
7. Proformas use their own number range, never post GL or stock, and expire like quotes; converting a proforma creates a real invoice with a fiscal number.
8. Reprints always watermark "COPY" and increment a reprint counter shown on the audit trail; only the first print renders as original.
9. Posting an invoice for stock lines writes `SALE` ledger entries and releases matching reservations in one transaction.
10. Voiding is POS-shift-scoped only ([2.1](2.1-counter-sales-pos.md)); outside the shift window the only reversal path is a credit note.

## Edge Cases & Error Handling

- **Posting fails after number assignment** (DB error mid-transaction): the whole transaction rolls back including the number — sequence integrity is preserved because assignment and posting are atomic.
- **Two invoices posting simultaneously**: sequence row is locked; second post waits and takes the next number — no duplicates, no gaps.
- **Invoice dated in a closed period** (order fulfilled 31st, invoicing on the 2nd after close): system forces the date to the open period's first day with a notice, or Finance briefly reopens the period — backdating into closed periods is impossible.
- **VAT rate changes overnight**: drafts re-resolve at posting; posted lines keep their stored rate. The per-line snapshot means a mixed-rate transition day still reports correctly.
- **Customer disputes a posted line price**: resolution is a price-correction credit note; the invoice itself never changes.
- **Batch invoicing hits one bad order** (credit hold applied since fulfilment): that order is skipped with a reason on the batch report; the rest of the batch posts.
- **Email PDF fails** (invalid address): posting is unaffected; the failure lands on the invoice's activity tab for retry.
- **Stock ledger write fails on one line** (e.g. serial not selected): entire posting rolls back — never a fiscal document without matching stock movement.
- **Currency invoice for an export customer**: `exchange_rate` snapshots at posting; GL posts in base currency, document prints in customer currency, zero-rated VAT code applied per line.

## Key Tables

Invoices live in the shared sales tables (schemas in the [parent doc](../02-sales-pos.md#core-database-tables)):

- `sales_documents` — `document_type = 'invoice'` (or `'proforma'`), with `posted`, `due_date`, totals
- `sales_document_lines` — line-level VAT snapshot and totals
- `payments` — allocations against the invoice
- Fiscal number sequences (per branch, per type) back the gapless numbering
