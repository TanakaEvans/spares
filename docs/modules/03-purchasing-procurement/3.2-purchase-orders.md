# 3.2 Purchase Orders

> The formal, legally binding order document sent to a supplier, with revision control, currency handling, and value-based approvals. Part of [Module 3: Purchasing & Procurement](../03-purchasing-procurement.md).

## Purpose

The purchase order (PO) is the contractual commitment to a supplier: these parts, these quantities, these prices, delivered to this branch by this date. Everything downstream — the GRN, the supplier invoice, the AP payment — is validated against the PO, which makes PO accuracy the foundation of 3-way matching.

For a motor-spares business the PO carries detail that generic ERPs often skip: the *supplier's* part number per line (a Bosch distributor picks by Bosch code 0 986 452 041, not by our internal SKU for that oil filter), line-level expected dates (the brake pads ship this week, the clutch kits are on back-order), and currency with a locked exchange rate for import suppliers such as a Dubai-based OEM parts consolidator.

The PO also enforces spending control. Value thresholds route large orders through a second approval, revisions keep an auditable history when a supplier confirms different quantities or prices, and blanket orders let the buyer commit to a framework (e.g. 200 oil filters per month from the local Fram agent) with individual releases against it.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Buyer | Create, edit drafts, submit, email to supplier, amend/revise, receive-close own POs |
| Procurement Manager | Approve level-1 threshold POs; edit any PO; manage blanket orders |
| Branch Manager / Director | Approve level-2 threshold POs |
| Warehouse Clerk | Read-only (sees expected deliveries for receiving planning) |
| Finance (AP) | Read-only; sees PO totals during invoice matching |

## Workflow

```
Draft PO ──► Submit ──► [value > threshold?] ──► Approval (1 or 2 levels)
                              │ no                     │
                              ▼                        ▼
                        Email PDF to supplier ◄────────┘
                              │
                              ▼
                    Supplier confirms (supplier_ref captured)
                              │
              ┌───────────────┼────────────────┐
              ▼               ▼                ▼
        Full delivery    Partial GRNs     Cannot fulfil
              │               │                │
              ▼               ▼                ▼
          received         partial        Revised PO (Rev n)
              │               │
              ▼               ▼
          invoiced ──────► closed
```

1. **Draft** — Buyer builds the PO manually or from approved PR lines; supplier part numbers, costs and discounts default from the supplier price list.
2. **Submit / approve** — Totals below the level-1 threshold go straight to `submitted`; above it, one or two approvals are required before the PO can be sent.
3. **Send** — The PO is emailed as PDF (configurable terms template) to the supplier's orders address; send events are logged.
4. **Confirm** — The supplier's acknowledgement reference is recorded in `supplier_ref`; status moves to `confirmed`.
5. **Amend** — If the supplier cannot fulfil as ordered, the buyer issues a revision (Rev 1, Rev 2…); the previous revision is archived read-only.
6. **Receive** — GRNs (3.3) update `qty_received` per line; status tracks `partial` → `received`.
7. **Invoice & close** — Supplier invoice matching (3.4) marks the PO `invoiced`; closing cancels any outstanding lines.

## Fields & Validation

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| supplier_id | select | Yes | Active supplier, not on credit hold with us |
| branch_id | select | Yes | Valid delivery branch |
| currency_id / exchange_rate | select / decimal | Yes | Rate > 0; defaults from currency table; locked after submit |
| expected_date | date | Yes | ≥ order_date; warning if < supplier standard lead time |
| supplier_ref | text | No | Max 100 chars; required before status `confirmed` |
| line: part_id | part search | Yes | Active part; must be linked to this supplier (override with warning) |
| line: supplier_part_number | text | No | Auto-filled; editable; max 100 chars |
| line: qty_ordered | decimal | Yes | > 0; warning if below supplier MOQ for the part |
| line: unit_cost | decimal | Yes | > 0; variance > 15% vs last cost raises an amber flag |
| line: discount_pct | decimal | No | 0–100 |
| line: expected_date | date | No | Defaults from header; ≥ order_date |

## Business Rules

1. A PO in `submitted` or later status cannot have lines deleted; quantities may only be *reduced*, and any change after `confirmed` produces a new revision with an incremented `revision` number.
2. The exchange rate is locked at PO date; differences at GRN/invoice time post as foreign-exchange variance, never as a cost change on the PO.
3. Two approval levels: level 1 (procurement manager) above threshold A, level 2 (director) above threshold B; thresholds are configurable per branch and evaluated on `total_incl` in base currency.
4. Closing a PO cancels all outstanding lines, releases any special-order reservations, and notifies the requisition owner for each affected PR line.
5. A revised PO keeps the same `po_number` with a "Rev n" suffix on the printed document; only the latest revision is receivable.
6. Blanket orders cannot be received directly — only their release POs can.
7. A PO cannot be cancelled once any GRN references it; it must be closed instead (preserving the received lines).

## Edge Cases & Error Handling

- **Supplier confirms a higher price than ordered**: the buyer must issue a revision before receiving; the GRN posts at PO cost, so receiving against the old revision would understate stock value. The system warns if `supplier_ref` is captured while line costs differ from the confirmation.
- **Approval threshold changed while a PO is mid-approval**: the threshold at submission time governs; a note in the approval trail records the threshold used.
- **Approver is also the buyer**: self-approval is blocked; the PO escalates to the next role up.
- **Email to supplier bounces**: the send log records the failure and the PO gains a "delivery failed" banner; the buyer can resend to a corrected address (supplier master update prompted).
- **Duplicate PO to the same supplier for the same part within 7 days**: warning banner at submit listing the overlapping open PO lines.
- **Currency devalues sharply before delivery**: the PO is unaffected (rate locked); the variance surfaces on the supplier invoice as FX variance — see [3.4](3.4-supplier-invoices.md).
- **Supplier delivers against Rev 0 after Rev 1 was issued**: the GRN screen only offers Rev 1 quantities; over-delivery handling (3.3) governs any excess.
- **All lines cancelled on revision**: the PO auto-closes and the originating PR lines revert to `approved` so they can be re-sourced.
