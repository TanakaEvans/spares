# 3.1 Purchase Requisitions

> Internal requests to buy parts, raised by the floor or auto-generated from reorder alerts, and approved before conversion to purchase orders. Part of [Module 3: Purchasing & Procurement](../03-purchasing-procurement.md).

## Purpose

A purchase requisition (PR) is the controlled entry point into the buying process. Nobody in the business orders stock directly from a supplier; instead, need is captured as a requisition — either automatically, when the reorder engine detects that stock of a fast-moving line such as NGK BKR6E spark plugs has dropped below its minimum at the branch, or manually, when a counter salesman takes a special order for a part not normally stocked (e.g. a turbo actuator for a Toyota Hilux 2.8 GD-6 that must be sourced from the Toyota parts distributor).

Requisitions separate *identifying the need* from *committing money*. The requester states what is needed and by when; the buyer decides which supplier gets the business, at what cost, and whether the request is justified. This prevents duplicate ordering across branches, keeps special orders traceable back to the customer who asked for them, and gives management a single queue of pending demand to review each morning.

Because a requisition carries the suggested supplier and the last purchase cost per line, the buyer can approve most requisitions in seconds and reserve real effort for high-value or unusual requests, which route through a manager approval step.

## User Roles & Permissions

| Role | Access |
|------|--------|
| Counter Sales / Warehouse Clerk | Create and submit requisitions; view own requisitions |
| Buyer | View all; edit lines, change supplier, approve within authority limit, convert to PO |
| Branch Manager | Approve requisitions above buyer authority threshold; cancel any requisition |
| Procurement Manager | Full access all branches; configure approval thresholds |
| System (Reorder Engine) | Auto-create requisitions with `source = auto` |

## Workflow

```
Reorder alert / manual need
        │
        ▼
  Create PR (draft) ──► Submit ──► Buyer review
                                      │
                    within authority? ├── yes ──► Approved
                                      │
                                      └── no ───► Manager approval ──► Approved
                                                        │
                                                   (rejected ──► back to draft)
        Approved ──► Buyer splits lines by supplier ──► Convert to PO(s)
                                                              │
                                                              ▼
                                                      PR status: converted
```

1. **Create** — The reorder engine or a staff member creates a PR with one line per part. Special orders capture the customer and sales order on the line.
2. **Submit** — The requester submits; the PR locks for the requester and enters the buyer queue, sorted by priority (`critical`, `urgent`, `normal`) then required date.
3. **Review** — The buyer checks each line: quantity sanity, suggested supplier, estimated cost (pulled from the last PO for that part/supplier).
4. **Approve** — If the estimated total is within the buyer's authority limit, the buyer approves directly; otherwise the PR routes to the branch manager.
5. **Convert** — The buyer selects approved lines (possibly a subset), groups them by chosen supplier, and generates one PO per supplier. Each converted line stores `converted_to_po_line_id`.
6. **Close** — When every line is converted or cancelled, the PR status becomes `converted`.

## Screens

| Screen | Route | Purpose |
|--------|-------|---------|
| Requisition list | `purchasing.requisitions.index` | Queue of PRs filtered by status, branch, priority |
| Create/edit requisition | `purchasing.requisitions.create` | Header + line entry with part search |
| Requisition detail | `purchasing.requisitions.show` | Review, approve, convert-to-PO action |

**Primary screen — Requisition detail.** Header band shows PR number, branch, requester, priority badge, required date, and status chip. Main area is the line grid: part number, description, qty requested, suggested supplier, estimated unit cost, line estimate, and a customer/sales-order tag for special-order lines. Right rail shows the approval trail (who, when, comment). Footer actions are contextual: *Submit* (draft), *Approve / Reject* (submitted, for approvers), *Convert to PO* (approved, opens the supplier-split dialog), *Cancel*.

## Fields & Validation

| Field | Type | Required | Validation rules |
|-------|------|----------|------------------|
| branch_id | select | Yes | Must be a branch the user is assigned to |
| required_date | date | Yes | Today or later; warning if < supplier lead time for any line |
| priority | select | Yes | `normal` / `urgent` / `critical`; special orders default `urgent` |
| notes | textarea | No | Max 1000 chars |
| line: part_id | part search | Yes | Active part; duplicate part on same PR blocked |
| line: qty_requested | decimal | Yes | > 0; warning if > 3× average monthly usage |
| line: suggested_supplier_id | select | No | Must be on the part's approved supplier list |
| line: estimated_unit_cost | decimal | Auto | Defaulted from last PO cost; editable by buyer only |
| line: customer_id / sales_order_id | lookup | Conditional | Both required together for a special-order line |

## Business Rules

1. Auto-generated requisitions (`source = auto`) are approved automatically when the estimated total is within buyer authority; otherwise they queue like manual PRs.
2. Special-order lines (customer + sales order attached) are forced to `priority = urgent` and cannot have their quantity reduced below the customer's ordered quantity without cancelling the linked sales order line first.
3. A line, once converted to a PO line, is immutable and cannot be converted a second time; the convert dialog hides already-converted lines.
4. One PR may be split across multiple suppliers, producing multiple POs; the PR only reaches `converted` when no open lines remain.
5. Approval authority is evaluated on the *estimated* total at approval time; if the buyer later raises the PO at a higher cost that crosses the threshold, PO-level approval (rule 3.2) still applies — PR approval does not bypass it.
6. Cancelling a PR with a linked sales order notifies the salesperson who owns the order.
7. Editing lines after submission resets the PR to `submitted` and voids any prior manager approval.

## Edge Cases & Error Handling

- **Reorder engine fires twice for the same part** (e.g. overnight job re-run): the engine checks for an existing open auto-PR line for the same part/branch and tops up its quantity instead of creating a duplicate.
- **Part discontinued between submit and approval**: the line shows a "part inactive" warning; the buyer must substitute (via the superseded-part link) or cancel the line — approval of an inactive-part line is blocked.
- **Suggested supplier no longer approved for the part**: conversion dialog blocks that supplier and prompts for reselection; the price-comparison panel (3.8) is offered inline.
- **Requester quantity typo (500 instead of 50)**: the >3× monthly usage warning highlights the line in amber; the buyer can amend the quantity — the change is written to the PR audit trail with old/new values.
- **Customer cancels the special order after PR approval but before PO**: cancelling the sales order line flags the PR line "orphaned special order"; the buyer chooses to cancel the line or convert it to normal stock replenishment.
- **Manager rejects**: PR returns to `draft` with a mandatory rejection comment; the requester is notified in-app.
- **Two buyers open the same PR**: optimistic locking — the second save fails with a "requisition was updated by {user}" error and a reload prompt.
